# 智水 · Android 版

完美校园「智慧用水 → 洗澡」的精简客户端。一个图标，打开就是洗澡页：无开屏广告、无首页瀑布流、不需要 root、不需要原版 App。

> ⚠️ **1.0.3 已撤回，请勿使用。**
> 该版本的「检查更新」里带两个第三方 GitHub 加速代理，其中 `ghproxy.cn` 在移动网络下会**跳转到色情网站**。
> 已经装了 1.0.3 的：请直接安装最新版，**不要在检查更新里点「镜像 1 / 镜像 2」**——那两条就是被劫持的域名。
> 主按钮「下载新版 APK」走的是 GitHub 直链，本身没问题，但那个直链在很多移动网络下打不开，所以最快的办法是用下面给出的 CDN 地址手动下载。

> 起因很小：官方入口里「淋浴」和「洗澡」是两个页面，从「淋浴」切到我们实际在用的「洗澡」还得多点一次；再加上开屏广告和几层菜单，去洗个澡要在手机上戳七八下。这个工具只做「洗澡」这一件事——打开就是它。
>
> **关于那个开屏广告，实际用起来比「有广告」更糟。** 一次实测录屏（52 秒）里数到的顺序是：开屏页（logo + 插画）→ **广告**（蚂蚁阿福助手 / 美团游戏 / 天猫双11，各带「跳过」倒计时）→ 首页。光是这三个广告就占了十几秒。更麻烦的是：只要预约成功后把 App 切到后台几秒钟，再切回来，它又会重新播一遍开屏 logo 和广告，之后才回到之前那个预约成功的页面。也就是说**这个广告不是「打开时看一次」，而是「每次从后台回来都要再看一次」**——等于每次回来看验证码，都得先看完一段广告。
>
> 顺带一个对照实验：同一段录屏里把「设备动作与方向」权限分别设成三种状态各启动一次。**三段耗时基本一致（分别约 7.5 秒、8.5 秒、9.5 秒），流程也都是「开屏页 → 广告 → 首页」，没有哪一种状态是必然更慢的。** 期间第二段有一次点「跳过」，结果跳进了**美团页面**，而完美校园自己则提示「进入后台运行」；这个现象经反复测试确认是**偶发**的，不是「仅开屏时不允许」这一档特有的问题。
>
> 还有一条更隐蔽的：官方预约时会报「不能早于当前时间」，手机时间明明正常。根因不在时钟，而在官方把预约时间的默认精度从**分钟**改成了**秒**——原本 1 分钟的容错窗口被压成 **1 秒**，手速稍慢就必然失败。这个报错是官方网页自己抛的，服务端根本不管。本项目干脆不显示时间选择，直接以服务端时间提交，问题不再存在。成因见 [docs/DEVELOPMENT.md 3.3.1](docs/DEVELOPMENT.md)。

> **关于本项目**：这是一个 AI coding 项目。作者此前没有相关开发经验，从界面、协议到构建、审计与文档，全程都是通过与 AI agent 用自然语言交流完成的。

## 功能

- 手机号 + 短信验证码登录（登录后不再依赖原版 App）
- 余额、当前预约（验证码 + 当日有效的失效倒计时）
- 浴室列表按宿舍号排序；可星标自己住的宿舍楼，列表只显示该楼浴室（A/B 区合并为同一栋，某个区设备坏了可去同楼另一区）
- 一键预约 / 取消预约
- 消费限时、限额设置：滑块 + 文本框联动；金额按浴室实际扣费的 0.05 元一档递增；保存后自动取消已有预约（订单带预约时的数值，不重新预约不生效）
- 最近 6 个月用水记录
- **检查更新**：多通道探测 GitHub（官方接口 → CDN 清单 → APK 内置清单 → 上次缓存），GitHub 打不开时也照样能给出最新版本、下载地址与 SHA-256；下载加速走 jsDelivr，安装包可通过系统下载器直接下载
- 深色模式自适应
- 下拉刷新：在页面顶部下拉即可手动更新余额与预约

## 目录结构

```
AndroidManifest.xml
src/com/wanmei/bath/
    MainActivity.java   WebView 容器 + JS 桥 + 页面路由
    Api.java            智慧用水业务的协议实现（会话、预约、记录、限时限额）
    Login.java          登录流程实现（建立会话、参数加密、签名）
    Store.java          SharedPreferences 读写
    Update.java         检查更新（多通道探测 + 内置清单/缓存兜底）
assets/index.html       界面（HTML + JS，走原生桥调 Java）
assets/latest.json      版本清单（断网时也知道最新版本与下载地址）
res/                    主题、颜色、图标
tools/
    build.sh            手工构建 APK（不依赖 Gradle）
    audit_apk.py        打包后自检：确认不含个人信息
```

界面就是 `assets/index.html`，改样式/文案直接改它，然后重新构建。里面的请求统一走 `Android.apiAsync(...)` 桥到 Java 层。

> Android 版和网页版的界面是各自维护的（网页版走 `fetch`，这里走原生桥），改动需要分别在两端进行。

## 构建

需要：JDK 8+、Android SDK（build-tools + platform）、Python 3、bash（Windows 用 Git Bash）。

```bash
# 1) 指定 SDK（三种方式任选，具体看你的目录结构）
export ANDROID_SDK=/path/to/android-sdk
# 或分别指定
export ANDROID_BUILD_TOOLS=/path/to/build-tools/34.0.0
export ANDROID_PLATFORM=/path/to/platforms/android-34

# 2) 构建（产物 build/bath.apk）
bash tools/build.sh

# 3) 自检（可选，建议每次都跑）
python tools/audit_apk.py --config ../web-app/config.json
```

首次构建会自动生成签名证书 `keystore/bath.keystore`（已在 .gitignore）。密码默认 `bath123`，可用 `KEYSTORE_PASS` 覆盖。**这个证书不要提交**，丢了就没法覆盖安装。

## 实现要点

- **界面**是本地 HTML（`assets/index.html`），WebView 里跑，通过 `@JavascriptInterface` 调原生网络层
- **网络与协议全在 Java**：不依赖任何第三方库，APK 约 45 KB
- **登录拿到的会话，就是业务接口要的凭据**：先建立会话，再在同一个会话里提交短信验证码，服务端会把它升格为账号会话
- 业务请求需要携带会话标识、时间戳，以及由前两者算出的签名；签名规则与常量不在 README 展开，实现见源码
- 登录与业务都用 Java 原生实现，不依赖任何第三方库，也不需要 Node.js
- 预约时间用**服务端返回的时间**计算，不用本机时钟——原版 App 的「预约时间不能早于当前时间」报错，根因是它把预约时间的默认精度改成秒，使容错窗口只剩 1 秒（与本机时钟快慢无关，见 [docs/DEVELOPMENT.md 3.3.1](docs/DEVELOPMENT.md)）
- 权限只有 `INTERNET` 和 `ACCESS_NETWORK_STATE`，无 Service / Receiver / Provider，`allowBackup=false`

## 隐私

- 安装包里**不含任何个人信息**：只有界面、协议代码和图标
- 登录后 session、姓名、学号、学校存在应用私有目录的 SharedPreferences 里，其他应用和 adb 都读不到
- 不采集设备信息、不埋点、不联网上报

## 已知限制

- **单点登录**：这里登录会让手机上的原版 App 下线（错误码 `100600`），反之亦然
- **充值只给指引**：原版走微信小程序支付，微信对 `appid + 包名 + 签名` 三重校验，第三方调不起，所以页面上只提示「微信搜索小程序：完美校园」
- 只有 Android 端；iOS 需要另做（协议层可复用）
- **跨校适配**：目前只在一所学校实测，其他学校的命名与扣费规则可能不同，见「适用范围与其他学校」

## 适用范围与其他学校

> **目前只在一所使用「完美校园 智慧用水」的学校实测通过。** 其他学校欢迎试用并反馈，但不保证开箱可用。

协议层基本是通用的：登录与业务都走完美校园的公共服务，签名规则固定；学校码、一卡通号、学号这些标识**不是写死的**，由短信登录返回，并在换取会话时被服务端下发的值覆盖。所以别校用户用自己的账号登录，主流程（登录、余额、预约、取消、记录）大概率能直接跑。

但以下三处是按我们校区的实际情况固化的，换学校（甚至换校区）都可能需要调整：

| 项目 | 目前的假设 | 别校可能的表现 |
| --- | --- | --- |
| 浴室命名 | 「一号宿舍a区 / b区」这类名称；`dormNo()` 按「X号」中文或阿拉伯数字排序，`dormKey()` 剥掉末尾 `a区/b区` 合并楼栋 | 「1号楼」「东区浴室」「A栋」等命名会让排序失效、星标把每间浴室当成一栋楼（不会崩溃） |
| 扣费与档位 | 金额以 **0.05 元**为步进、范围 1.00–20.00 元；限时 1–120 分钟；原生端按「分」校验 `% 5 == 0` | 扣费单位若是 0.01 / 0.1 元，或官方档位上限不同，保存设置可能被拒或金额不对 |
| 固定业务参数 | `limittype=1`、`verificationtype=2`、`telephoneInfo=12`；验证码按「当日有效」倒计时 | 客户配置不同可能不生效，需按官方 H5 的实际值调整 |

**反馈请走 [跨校适配反馈模板](https://github.com/ghg6666678/wanmei-bath-android/issues/new/choose)**，按模板提供学校/系统名称、几个浴室名称样例、扣费单位和具体表现。积累两所以上学校的真实数据后，再把这些项外置成配置，避免凭猜测改代码。

> issue 是公开的：**不要粘贴手机号、学号、姓名、短信验证码、token/session 或完整的登录返回内容**。浴室名称可以贴，日志和截图请先打码。

### 想集成到自己的校园工具？

欢迎。只要满足一个前提——**每个使用者登录自己的账号，凭据不集中在你手上**——那就属于许可里明确允许的情形，不必额外申请。

**如果你只是被浏览器跨域卡住**——需要一台服务器转发、但不打算留存任何票据——那也不用申请。许可第 4 条专门写了这个情形：不落盘、不写进日志、不跨用户共享、一次请求只服务一个会话，这就是合法转发，不算「替他人登录」。转发和代登录是两件事，区别在于有没有**留下来**、有没有**给第二个人用**。

如果你需要的是「服务器代登录」这种形式，或者你的项目本身带有广告、会员这类商业成分，也欢迎开 Issue 谈——那种情况需要单独授权，但不是不能谈。说清四件事就行：项目是什么、大概多少人用、是否收费或有广告、账号怎么来的。许可里留了单独授权的口子，它不是一堵墙。

代码本身也没给这类用法留路：

- 预约是**单次点击**——一个请求对一个订单，提交期间按钮禁用，没有循环、没有并发、没有重试；
- 不维护账号池，**一个登录态只服务一个使用者**；
- 改设置后取消旧预约是**串行**执行的，宁可慢也不并发。

要拿它做批量操作，得自己改代码——那种用法不在许可范围内，也不在本项目讨论范围内。
