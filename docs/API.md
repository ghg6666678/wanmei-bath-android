# 接口说明

这个客户端要跟三类服务器打交道。本文说明**它跟这些服务器之间发生了什么、边界在哪**。

> **范围说明**：这是一份设计说明，不是对接手册 —— 请求地址、参数名、算法、命令名、响应字段一律不展开；需要看实现请直接读仓库源码。之所以这样处理，是因为第三方服务的使用条款通常禁止反向工程与再发布相关资料，本文只保留「做过什么、为什么这么做」。

| 分类 | 对方 | 用在哪 | 性质 |
| --- | --- | --- | --- |
| **A. 登录** | 校园平台的登录服务 | App 与网页端 | 第三方接口 |
| **B. 业务调用** | 校园平台的用水服务 | App 与网页端 | 第三方接口 |
| **C. 本机服务** | 自己跑的 `server.py` | 仅网页端 | 本项目自建 |
| **D. 版本检查** | GitHub 及其镜像 | App 与网页端 | 公开接口 |

App 端把 A、B 用 Java 实现（`Login.java` / `Api.java`），不经过 C；网页端把 A、B 放在 Python 里（`wxlogin.py` / `vwater.py`），浏览器只跟 C 通信。

# A. 登录（概述）

官方客户端登录后才能用水。本项目要做的是「不装官方 App 也能登录」，所以必须自己把登录流程实现一遍。

## A.1 三步，顺序不能换

| 步骤 | 做什么 | 为什么不能省 |
| --- | --- | --- |
| 1. 建立会话 | 客户端生成一对临时密钥交给服务端，换回会话标识与一份密钥材料 | 后续参数都要用它加密 |
| 2. 发送短信验证码 | 用会话标识签名后请求发码 | 短信是唯一的身份凭据 |
| 3. 提交验证码登录 | 手机号 + 验证码，换回账号资料 | 会话在这一步才真正绑定到账号 |

## A.2 每个请求都包一层信封

登录服务的业务请求都要签名：参数先加密，信封本身再算一个哈希值放进请求头。

两个容易错的地方：

- 签名算的是**信封**的紧凑 JSON，不是明文参数。多一个空格签名就错；
- 加密用的密钥材料来自第 1 步，不是写死的。

## A.3 登录之后拿到什么

解密后是一份账号资料：姓名、学号、学校编号、一卡通编号等。**这些字段要填到业务侧对应的位置**，填错会表现为「登录成功但业务接口说登录态失效」——这是本项目踩得最久的一个坑。

> 关键结论：**用水业务要的凭据，与登录会话是同一份**。只要在同一个会话内按顺序走完三步，它就能直接用于业务调用，不必再去别处取。这是整个项目从「依赖设备权限」转向「独立登录」的分水岭。

## A.4 为什么没做密码登录

协议上支持账号密码登录，实现也早写好了（`wxlogin.py` 里的 `login_pwd()`），但从未接入界面。原因见 [DEVELOPMENT.md](DEVELOPMENT.md)：验证码是一次性的，客户端不必留任何长期凭据。

# B. 业务调用（概述）

所有用水业务都汇总到**同一个入口**，靠请求里的一个命令字段区分功能 —— 不是一组 REST 接口，而是一个 RPC 式的总入口。

## B.1 两层结构

```
第一次：换取会话参数（一次跳转，服务端在响应里交回后续要用的标识）
之后：所有业务发到同一个地址，请求体里写明「做什么 + 参数」
```

每次业务请求都要带：会话标识、当前时间、以及由这两者算出的签名。签名规则与常量不展开。

两个容易漏的点：

- 会话标识有有效期，过期要重新换取；换取失败通常意味着登录态已失效；
- 业务调用返回空时，先重换会话再重试一次，多数情况就恢复了。

## B.2 能做什么

| 功能 | 说明 |
| --- | --- |
| 浴室列表 | 可用浴室、空闲设备数、营业时间 |
| 当前预约 | 预约记录与验证码 |
| 余额 | 单独查询（列表里那个余额字段是占位值，恒为 0） |
| 消费限制 | 读取与保存限时 / 限额 |
| 预约 / 取消 | 下单生成验证码，按订单号撤销 |
| 用水记录 | 按月查询明细 |

## B.3 几个业务事实

这些是实测与官方文案确认的行为，与接口怎么调无关：

- 验证码当日有效，可重复使用；
- 限时 / 限额从**开阀那一刻**起累计，超限后重输同一个验证码可以再开；
- 订单里冻结的是**下单当时**的限时 / 限额，所以改了设置必须重新下单才生效；
- 「预约时间不能早于当前时间」这个报错，是官方前端自己抛的，服务端并不校验；
- 官方报这个错时的**真实成因不是本机时钟不准**：**默认进入预约页时取到的时间带着真实秒数**，容错窗口只有 1 秒（手动选一次时间会变回 1 分钟，但多一步操作）。详见 [DEVELOPMENT.md 3.3.1](DEVELOPMENT.md)。本项目不显示时间选择，直接以服务端时间提交，彻底绕开这条比较；
- **充值无法复刻**：官方支付绑定了小程序标识、包名与签名三者，第三方客户端调不起。本项目只做「说明 + 打开微信」。

# C. 本机服务接口（仅网页端）

网页端由 `server.py` 提供，浏览器只跟它通信；它再拿 A、B 两套协议去请求官方服务器。零第三方依赖，只用标准库。

## C.0 约定

| 项 | 值 |
| --- | --- |
| 默认端口 | `8770` |
| 返回 | JSON，`Content-Type: application/json; charset=utf-8`，`Cache-Control: no-store` |
| 成功 | `{"ok":true, ...}` |
| 失败 | `{"ok":false,"error":"<人类可读的原因>"}` |
| 未登录 | `{"ok":false,"needLogin":true,"error":"..."}` |

## C.1 接口一览

> 下面这些是**本项目自己定**的接口，字段名部分沿用了上游的命名，但用途与含义以本节为准；这一节不涉及如何调用第三方服务。

| 方法 | 路径 | 作用 |
| --- | --- | --- |
| GET | `/api/state` | 一次性拿 配置 + 余额 + 预约 + 浴室列表 + 服务端时间 + 当前限制 |
| GET | `/api/config` | 只拿账号配置（不含 token） |
| GET | `/api/time` | 服务端时间与本地时间，用于校时 |
| GET | `/api/settings` | 当前消费限时 / 限额 |
| GET | `/api/records?month=YYYY-MM` | 用水记录 |
| POST | `/api/book` | 预约 |
| POST | `/api/cancel` | 取消预约 |
| POST | `/api/settings` | 保存限时 / 限额 |
| POST | `/api/config` | 覆盖写入配置（调试用） |
| POST | `/api/native` | 浏览器端模拟 App 原生调用（登录 / 退出） |
| GET | `/api/version` | 检查更新 |

## C.2 `/api/state`

`GET`，无参数。内部依次查浴室列表、余额与当前消费限制。

```json
{
  "ok": true,
  "config": {"name":"...","phone":"...","outid":"...","school":"...","hasToken":true},
  "balance": 12.34,
  "orders": [ ... ],
  "bathrooms": [ ... ],
  "serverTime": "183000",
  "settings": {"max_fare_limit":235,"max_time_limit":30},
  "limits": { ... }
}
```

`orders` 是当前预约（含验证码），`bathrooms` 是浴室列表（含空闲数与营业时间）；`balance` 查询失败时为 `null`。

## C.3 `/api/book`

`POST`

```json
{"bathroomcode":"<编号>","datetime":"2026-11-09 18:30:00","verificationtype":"2"}
```

服务端的把关（官方服务端不管这些）：

1. `datetime` 必须能解析，且**不早于服务端当前时间 2 分钟以上**，否则报错并给出服务端时间
2. 提交时间不得晚于该浴室的 `businessclosetime`
3. 限额/限时取用户在「我的」里设置的，而不是浴室默认值

> 关于第 1 条的 2 分钟容差：官方前端因为默认时间精度是秒，容错窗口只有 1 秒；这里放宽到 2 分钟，正是为了让人工填的时间、页面加载耗时和网络延迟都不至于误伤。对应的前端实现是**根本不显示时间选择**，直接提交服务端时间、秒位补 `0`。

成功响应：

```json
{"ok":true,"message":"预约成功","verificationcode":"123456","orderdatetime":"2026-11-09 18:30:00"}
```

## C.4 `/api/cancel`

`POST`

```json
{"orderno":"<订单号>"}
```

```json
{"ok":true,"message":"已取消预约"}
```

## C.5 `/api/settings`

`POST`

```json
{"time":30,"fare":2.35}
```

`fare` 单位是**元**（服务端内部换算成分）。校验规则与其他入口一致：`time` 1–120；`fare` 1.00–20.00 且必须是 0.05 的整数倍，或传 5000 表示不限。

## C.6 `/api/native`

`POST`，用于让网页端也能像 App 一样登录/退出（浏览器里没有 `Android` 对象）。

```json
{"name":"doLogin","args":["<手机号>","<验证码>"]}
```

| `name` | `args` | 说明 |
| --- | --- | --- |
| `sendCode` | `[手机号]` | 发送验证码 |
| `doLogin` | `[手机号, 验证码]` | 登录，成功后写入 `config.json` |
| `logout` | `[]` | 清除票据 |

响应统一为 `{"ok":true,"data":{}}` 或 `{"ok":false,"error":"..."}`。

## C.7 `/api/version`

`GET`，可带 `?force=1` 跳过缓存。服务端代查 GitHub（用户所在网络经常打不开），多通道并行探测，失败时退回随包发布的 `web/latest.json`，再退回磁盘缓存。

```json
{
  "ok": true,
  "current": {"version":"1.1.0","versionCode":0},
  "latest": {
    "version":"1.1.0","publishedAt":"2026-11-10T03:37:44Z",
    "notes":"...","apkName":"zhishui-1.1.0.apk",
    "apkUrl":"https://github.com/.../zhishui-1.1.0.apk",
    "sha256":"a6f8e6f0...",
    "mirrors":[
      "https://cdn.jsdelivr.net/gh/...@v1.1.0/release/zhishui-1.1.0.apk",
      "https://gcore.jsdelivr.net/gh/...@v1.1.0/release/zhishui-1.1.0.apk"
    ],
    "downloads":[{"url":"https://cdn.jsdelivr.net/...","ok":true,"ms":1204,"kind":"cdn"}],
    "releaseUrl":"https://github.com/.../releases/tag/v1.1.0"
  },
  "source": "GitHub 官方接口",

```

- `stale: true` 表示网络不通、数据来自本地清单或缓存
- 缓存 30 分钟；`stale` 结果只缓存 5 分钟，网络恢复后尽快重探

App 与网页端都会查 GitHub，通道与降级顺序见 [DEVELOPMENT.md 8.4](DEVELOPMENT.md#84-103检查更新)。这里只列地址：

| 版本清单 | `https://cdn.jsdelivr.net/gh/ghg6666678/wanmei-bath-android@main/latest.json` |
| 同上，备用节点 | `https://gcore.jsdelivr.net/gh/ghg6666678/wanmei-bath-android@main/latest.json` |
| 同上，raw | `https://raw.githubusercontent.com/ghg6666678/wanmei-bath-android/main/latest.json` |
| APK（Release 资产） | `https://github.com/ghg6666678/wanmei-bath-android/releases/download/v<版本>/zhishui-<版本>.apk` |
| APK（CDN，按 tag 定位） | `https://cdn.jsdelivr.net/gh/ghg6666678/wanmei-bath-android@v<版本>/release/zhishui-<版本>.apk` |

**不使用任何第三方加速代理。** 2026-11 曾引入过 `ghproxy.cn`、`ghfast.top` 和 `jsd.onmicrosoft.cn`，三个都已移除：

- `ghproxy.cn` 在移动网络下会跳转色情站点（1.0.3 因此被撤回）；
- `ghfast.top` 拒绝 API 路径，且同属不受控的免费代理；
- `jsd.onmicrosoft.cn` 实测是 **301 跳到 `raw.githubusercontent.com`**，本身不存内容，而 raw 在国内比 github 更难访问——它连「国内节点」这个名分都不成立。

判断一个「加速域名」是否可信，只看两件事：**响应头是 200 还是 30x**，以及 **`Server` 是 CDN 还是反代**。剩下的说法都不算数。

# E. 排查思路

按「先怀疑什么」排列，不涉及具体接口：

| 现象 | 先检查什么 |
| --- | --- |
| 登录成功，但业务接口说登录态失效 | 账号资料有没有填到正确位置；服务端重新下发的值有没有覆盖本地值 |
| 登录接口返回 200 但内容为空 | 参数的编码格式是否与服务端期望一致（格式错时服务端不报错，只回空，极难排查） |
| 所有请求都失败且没有响应体 | 会话是否已过期；重新换取会话后重试 |
| 余额一直是 0 | 是不是读了列表里的占位字段，而不是单独查询 |
| 改了限额但没生效 | 订单冻结的是下单时的值，需要重新预约 |
| 预约报「不能早于当前时间」 | 官方前端抛的，根源是**默认入口取到的时间带着真实秒数**（容错窗口仅 1 秒），与本机时钟无关；本项目已绕开 |
| 用着用着突然「掉登录」 | 会话有效期有没有处理 |

# F. 已知限制

- **单点登录**：完美校园一个账号只允许一个会话。在这里登录会让官方 App 下线，反之亦然。
- **接口非公开**：这些接口没有对外文档，官方随时可能调整参数或增加校验，届时需要重新对一遍。
- **只在一个校区实测**：学校码、一卡通号、学号都不是写死的，由登录返回；但浴室命名、扣费单位、限额档位可能因校区而异——本校不同校区用的系统都可能不一样。
- **不要高频请求**：会话与设备会被风控，实测高频调用会触发保护。本项目的刷新间隔是 3 分钟，另有 30 秒防抖。
- 本文只描述「发生了什么」，**不含任何账号、票据或个人信息的真实值，也不提供可直接复现的调用细节**。

# G. 蓝牙水控（调研结论，未实现）

官方还有一条「宿舍淋浴」的产品线，在部分学校是**蓝牙水控**：手机连上水控器直接开阀，不走验证码。

本项目**没有实现**这条路径。这一节只记录调研结论，不含实现细节。

## G.1 技术上可行，且比预想简单

关键在于：**加密不在客户端**。开阀指令由服务端生成，客户端只负责「把字节写给设备、把设备回包再问一次」。所以不需要自己实现一套私有加密算法，只需要 BLE 传输层加一个状态机。

## G.2 与本项目的关系

调研起因是有人提到本校某校区的水控是蓝牙的。核对结果：

- **我所在的校区**用完美校园的「洗澡」（公共浴室预约 + 验证码），实测可用，也就是本项目对接的那套；
- **本部**用的是另一家厂商的「趣智校园」，另一套系统、另一个 App。

两者不是同一套系统的两种接入方式，而是两家公司的产品。所以蓝牙方案在本部没有落点，跟本项目服务的校区无关。

> 顺带一提：仅凭设备外观**无法区分蓝牙与联网**，两种水控都可能长得一样。真正定案的是扫机身二维码后跳转的那个 App。

## G.3 为什么没做

- **没有设备可测**：协议只能靠推断，字节对不对只能靠设备回包确认，风险不可控；
- **要加权限**：BLE 扫描与连接会破坏「权限极简」这个取舍；
- **防蹭用设计**：蓝牙水控通常是挑战-响应加设备绑定，设备可能已被他人占用；
- **计费更敏感**：「平台下单 + 设备离线记账」两条线，错位风险比验证码模式高得多。

> 如果将来有学校确实是完美校园的蓝牙水控、又有设备可测，可以按上面的思路重新评估。本节不提供实现路径。

# H. 校园卡绑定（调研结论，未实现）

用户提出的需求：**把「绑定校园卡」也做进来**，否则第一次使用的人还得先下载官方 App、注册、绑卡才能用上本工具。

这一节记录调研结论。**结论是这条路暂时走不通，但原因不是技术难度，而是功能位置。**

## H.1 官方确实有一整套「校园卡」H5

在官方 App 的 WebView 缓存里能找到一个完整的独立 H5 应用（与「智慧用水」并列的另一套）：

| | 智慧用水 | 校园卡 |
| --- | --- | --- |
| 入口 | 首页 → 智慧用水 → 洗澡 | 我的 → 校园卡 |
| 页面标题 | 智慧用水 | **校园卡** |
| 提供的功能 | 浴室列表、预约、消费记录 | 交易明细、卡挂失、捡卡登记、改查询密码、圈存、消费统计、日账单、余额同步 |

这套 H5 的接口体系与智慧用水**完全不同**，而且**简单得多**：

- 请求方式是 `POST` 到一个固定路径，参数只有三项：一个 token、一个接口名、一个 JSON 字符串；
- **没有加密、没有签名、没有会话票据** —— token 直接来自页面 URL。

也就是说，**这套接口本身是可以直接调用的**，实测能正常返回一卡通余额、卡号、交易与账单数据。

## H.2 但它只有「已绑卡之后」的功能

问题在于：这套 H5 里**没有「申请绑定」的接口**，只有两个相关的：

| 接口 | 作用 |
| --- | --- |
| 查绑卡记录 | 列出这个学号下注册过哪些账号 |
| 申请解绑 | 把卡解绑 |

「绑定」这个动作本身不在这里。再看这套 H5 声明要跳转的原生页面，全部是**原生 Activity**（交易明细、捡到卡、卡挂失、修改查询密码，四个都在同一个「校园卡」功能包下）—— 没有一个是 H5。

也就是说，**校园卡的业务能力整体是原生实现**，H5 只是「已绑卡之后」的账户页。

进一步的旁证：厂商自己提供的「一卡通」服务，开通步骤第一句就是「打开官方 app，**绑定自己的校园卡**」——**官方渠道同样要求用户先在 App 里绑**。

## H.3 为什么没有继续追

「申请绑定」这个动作，要拿到只能在原生侧找。原生侧有三重障碍：

1. **证书固定**：官方 App 做了证书校验（SSL pinning），装系统证书抓包会被直接拒掉 —— 这一条在开发早期就撞过墙，是确定的结论，不是猜测；
2. **加固**：安装包带加固壳，代码本身是加密的，静态读不出接口；
3. **合规边界**：本项目只做「读明文前端里已有的公开接口」，不脱壳、不逆向原生代码。

在 H5 侧穷举接口名也验证过了：候选的绑卡接口名全部返回「命令验证失败」（即不存在），而同一套接口里已知存在的接口调用正常。

**结论：「申请绑定校园卡」是原生 App 独占的能力，没有对应的 H5 接口可以对接。**

## H.4 顺带查清的一件事：现有工具本来就隐含了「已绑卡」这个前提

这条比上面的结论更有用。

本项目的登录接口返回的用户对象里，带着两个字段：

- 一个是**一卡通客户号**；
- 一个是**学号**。

而服务端在登录后**强制要求这两个字段非空**，缺任一个就判定为「还没有登录，请用手机号登录」。

也就是说 —— **一个从未绑过校园卡的用户，在本项目里登录后是进不去的**：登录会成功，但会因为缺少这两个字段而被拦在门外。

所以「首次使用要先下载官方 App」这个门槛，**在当前版本就已经存在**，只是没有在界面上说清楚。

要真正降低这个门槛，只有两条路：

1. **补上绑卡**（受阻于上面三重障碍）；
2. **把提示做清楚**：在没有这两个字段时，明确告诉用户「需要先在官方 App 里绑定校园卡」，而不是笼统地说「还没有登录」。

第 2 条没有技术障碍，只是文案。

## H.5 换了个思路：微信小程序也能绑卡

上面第 2 条落地时，又查到一条更有用的信息 —— **官方的小程序同样提供校园卡绑定**，流程和 App 一致：

> 微信搜「完美校园」小程序 → 选择学校 → 首页点「绑定校园卡」→
> 依次输入姓名、学工号、校园卡密码 → 确认

校园卡密码一般是身份证后六位，末位是字母 `X` 的按 `0` 填。（各家学校指引措辞略有差异，但流程一致。）

于是「不想装官方 App」这条路就通了：**用户用微信小程序绑好卡，再回到本 App 用手机号登录即可**，全程不需要装原版 App。

小程序的局限也要说清楚：它首页只有「扫一扫」「充值」「课程表」「学生权益」等入口，**没有「智慧用水」功能**，不是完整版程序 —— 只能用来绑卡，洗澡还是得回本 App。

## H.6 本次落地

在两个时机给出这条指引：

| 时机 | 行为 |
| --- | --- |
| **首次启动** | 弹一次引导弹层，说明小程序绑卡流程；标记存原生偏好（网页端存 localStorage），看过一次就不再弹 |
| **登录后** | 若发现该账号还没绑校园卡（缺一卡通客户号或学号），提示「登录成功，但账号还没绑校园卡」并弹出同一张引导 |
| **未登录占位页** | 增加「怎么看绑校园卡？」按钮，随时可以再看一遍 |

### 弹层上的两个按钮

初版是「稍后再说 / 知道了」，两个都只做关闭 —— 实际用起来是同一个动作，白占一个按钮位。

现在改成：

| 按钮 | 行为 |
| --- | --- |
| **打开微信**（描边） | 拉起微信让用户去小程序绑卡。**不关弹层、不写「已看过」** —— 从小程序回来还要照着上面的步骤做，关掉就看不见了 |
| **知道了**（实心） | 关闭弹层并记下「已看过」，下次启动不再弹 |

「打开微信」走的是充值弹层同一条路径：原生 `openUrl('weixin://')` → `handleScheme` → `ACTION_VIEW`。1.5 秒后仍停在 App 内说明没拉起来（多半没装微信），补一条提示。浏览器端没有原生桥，退化成一句「请在微信中搜索小程序『完美校园』」。

> 这里没有沿用 `guideLater` 这个 id 而改成 `guideWx`，是为了让「点它会发生什么」在代码里也读得出来 —— 一个叫「稍后」的按钮实际在打开微信，下一个人会被误导。


同时把服务端「还没有登录，请用手机号登录」这一句拆成两种情况：

- 缺登录凭据 → 照旧提示「还没有登录」；
- **登录成功了但缺校园卡信息 → 明确告知「这个账号还没绑定校园卡」**，并给出小程序与 App 两条路径。

原先这两种情况返回同一句话，用户完全不知道该做什么 —— 这是「首次使用门槛」一直存在却没人提的真正原因：不是功能缺失，是**没说清楚**。



## H.7 「验证码当日有效」按谁的日历算？（跨日边界问题）

### 现象

服务器时间与用户本地时间不一致（本例慢 15 分钟）时，出现：

- 过了本地时间的 0 点，预约**没有**失效；
- 到了服务器时间的 0 点，预约才失效。

### 先分清两件事

| | 谁决定 | 我们能不能改 |
| --- | --- | --- |
| **验证码在设备上还能不能用** | **服务器**按它自己的日历日判定 | ❌ 改不了，是服务端业务规则 |
| **App 里那句「还有 X 分钟后失效」** | 我们自己算的 | ✅ 能改 |

核实过前端**不做任何按时间过滤**（`state.orders` 里返回什么就渲染什么），所以「服务器 0 点后预约消失」是**服务端真的不再返回该订单**，不是显示问题。

### 关键约束

「当日有效」里的「当日」不能简单改成「本地时间的那一天」—— 那会造成**显示说已失效、设备上却还能用**，比现在更糟。

也不能改成某个固定的绝对时刻 —— 不同学校的服务器时区不一样，硬编码会伤到时区正常的学校。

### 采取的办法

**失效点严格跟着「服务器自己的日历」走，但用本地时间来表达它。**

服务器按它自己的日历日切验证码，这一点改不了也不该改 —— 如果按本地日历切，会出现「显示已失效、设备上却还能用」，比现在更糟。

所以做的是：**服务器什么时候失效，我们就什么时候失效；但把那个时刻换算成本地时间显示**，用户能对照自己的钟。

实现上不拼绝对时刻，而是**只算还剩多久**：

```
剩余 = (到 24:00:00 的秒数) - 1 秒        ← 只依赖服务端的时分秒
本地失效点 = 本地当前时刻 + 剩余
```

这样避开了两个坑：

- **「服务端是哪一天」无从得知** —— 服务端当前时间只给时分秒（`nowdate`），没有日期，而它与本机的时差可能跨过午夜，直接拼日期会差一天；
- **亚秒级校时误差被放大** —— 校时只能精确到秒，这个误差在 23:59:59 边界上会被放大成「差一整天」。

改成算差值之后，日期和时区都不参与了，剩下的差值只由时分秒决定，**精度与服务器判定完全一致**。

### 验证

用受控时间逐个跑过下列场景，每个场景都检查「失效点换算回服务端时间是否正好是 23:59:59」：

| 场景 | 服务端此刻 | 本地失效点 | 换算回服务端 |
| --- | --- | --- | --- |
| 服务端慢 15 分钟 | 23:55 | 次日 00:14:59 | 23:59:59 ✅ |
| 服务端慢 15 分钟（已跨日） | 00:05 | 次日 00:14:59 | 23:59:59 ✅ |
| 服务端慢 15 分钟 | 12:00 | 次日 00:14:59 | 23:59:59 ✅ |
| 时区正常 | 23:55 | 当天 23:59:59 | 23:59:59 ✅ |
| 时区正常（已跨日） | 00:05 | 当天 23:59:59 | 23:59:59 ✅ |
| 服务端快 30 分钟 | 12:00 | 当天 23:29:59 | 23:59:59 ✅ |
| 服务端慢 1 分钟 | 23:59:30 | 次日 00:00:59 | 23:59:59 ✅ |

**时区正常的学校完全不受影响**（显示仍是「当天 23:59 失效」），跨时区的学校显示的是换算后的本地时刻，与服务器行为严格一致。

### 下单前提醒：快到日切点了就说清楚

失效点跟着服务端日历走，意味着**越晚下单，验证码能用的时间越短**：23:50 下单，码只活二十几分钟。这一点本身没错（服务端就是这么判的），但用户下单时看不到，容易误以为「今天约的，今天什么时候去都行」。

所以在预约弹层里加了一条提醒，条件按**剩余有效期**判断，而不是按钟点：

- 剩余 < 60 分钟 → 在提示块首位显示：**「验证码当日有效：这次预约只到 00:15 失效（还剩 25 分钟）。如果你打算过了这个点再去，可能就来不及了。」**

为什么不用「晚上 11 点后提醒」这种写法：各校服务器零点相对现实的偏移不同（有的慢十几分钟、有的快几分钟），固定的钟点阈值必然有的学校提醒太早、有的太晚。而「离服务端零点还剩多久」正好等于「新码能活多久」，是个与学校无关的量，一套逻辑通吃。

这条只是**信息**，不改变任何行为：不拦截下单、不自动作废、不额外弹确认。风险交给用户判断，但前提是把「几点失效、还剩多久」说明白——含糊的「注意风险」等于没提醒。
