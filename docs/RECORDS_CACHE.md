# 消费记录：本地缓存与增量刷新（设计稿）

> **状态：设计稿，未实现。** 写这份文档的目的是把方案和它带来的代价一起摆清楚，再决定做不做。

---

## 一、先说一个比「重复拉取」更基础的问题

现在记录页每选一个月，只发一次请求：

```js
api('/api/records?month=' + recMonth)          // 不传 page
```

服务端默认 `page=1, rows=20`，前端**从来没有翻过页**，也没有「加载更多」。

也就是说：**每个月只能看到前 20 条记录。**

一天去两次浴室，一个月就是 60 条。对这类用户，现在的记录页本身就是不完整的——不是"加载慢"，是"看不全"。

这件事的优先级高于缓存。缓存一个只有 20 条的数据，只是把这个缺陷存下来。

## 二、目标

1. 记录**拉全**（翻页直到没有更多）
2. 已经拉过的月份**不再重拉**，秒开
3. 只有「可能发生变化」的月份才刷新
4. 多账号不串数据
5. 不新增任何上传行为

## 三、方案

### 3.1 数据模型

接口按月返回，没有全局唯一 id。所以**月份是天然的存储单位**：

```js
// localStorage: key = "rec:<账号哈希>:<YYYY-MM>"
{
  month: "2026-11",
  items: [ {opfare, end_opdt, termid, termname, status}, ... ],
  totalFare: 123.45,
  fetchedAt: 1731288000000,
  complete: true          // 关键：只有真正翻完所有页才置 true
}
```

- **记录本身不需要唯一键**——刷新时整月替换，不做逐条合并。理由见 4.4。
- `complete: false` 的月份不参与"命中缓存直接渲染"，否则会显示半份数据还让人以为全了。

### 3.2 什么时候拉，拉哪些

| 月份 | 策略 |
| --- | --- |
| 当前月 | 每次进页面都刷（今天可能又有新记录） |
| 上个月 | 同一天内只刷一次（可能有补录） |
| 更早 | 缓存 30 天有效，过期才重拉 |
| 用户手动下拉 | 强制刷新当前月 |

这样日常使用是：**打开就显示，后台悄悄刷当前月**。

### 3.3 翻页拉全

```js
let page = 1, all = [];
while (page <= 10) {                    // 上限防死循环
  const j = await api(`/api/records?month=${m}&page=${page}&rows=50`);
  const rows = j.data?.data || [];
  all = all.concat(rows);
  if (rows.length < 50) break;          // 最后一页
  page++;
}
```

`rows` 提到 50（默认 20 太小），上限 10 页 = 500 条/月，够用且不会失控。

### 3.4 存在哪

**localStorage**，不用 IndexedDB：

- `setDomStorageEnabled(true)` 已经是开的，`setDatabaseEnabled(false)` 不影响 localStorage
- 数据量小：6 个月 × 60 条 × 约 200 字节 ≈ 70KB，离 5MB 上限很远
- 同步 API 在这个数据量下不卡

代价：可能被系统清理（清应用数据）。这是**可接受的**——缓存本来就不是权威数据，丢了重拉即可。

### 3.5 账号隔离

key 里的账号标识用 **`sha256(outid)` 的前 16 位**，不存明文学号：

```js
const accountKey = await sha16(state.config.outid || 'unknown');
```

- `outid` 由服务端在 `entrance` 时下发，换账号必然不同
- 哈希不可逆，避免在设备上留明文身份信息
- **但要说清楚：这不是强匿名**。知道学号的人可以暴力验证——它只防"随手翻文件看到"，不防"已经知道答案的人"

## 四、与现有设计的五处冲突

这一节是重点。方案本身不难，难的是它和已经写进 README 的那些承诺之间的关系。

### 4.1 隐私承诺

README 现在写的是「不采集、不上传、安装包不含个人信息」。

本地缓存消费记录**不是上传**，但它确实把「什么时候洗了多久花了多少」落在了设备上。需要同步调整措辞，否则就是自相矛盾。

建议改成：

> 记录缓存只存在你自己的设备上，不上传、不统计、不跨设备同步；可以在「我的 → 清除本地缓存」里一键删掉。安装包本身不含任何数据。

关键是**给一个一键清除的入口**，否则"只在本机"听起来像推脱。

### 4.2 单账号假设

现在的设计是单账号：换登录会覆盖配置，没有"账号切换"。所以：

- 缓存按账号隔离在**技术上**没问题
- 但用户在设置里退出登录时，**缓存要不要一起清？**

建议：退出登录时**保留**（同一台设备大概率还是同一个人），但提供一个明确的清除按钮。如果哪天做了多账号切换，那时再按 key 自动隔离即可。

### 4.3 无状态模式（网页端）

`BATH_STATELESS=1` 的核心承诺是「服务端不保存任何用户数据」。

如果记录缓存在服务端，就直接违背这条。所以：

**记录缓存只能放在浏览器 localStorage，服务端永远不参与。**

好在两端共用同一份前端代码，Android 和网页端可以用同一套逻辑——网页端的差异只是"服务端不落盘"。跨设备不同步，这是必然的取舍。

### 4.4 记录会变

这是增量方案最容易被忽略的地方：**记录不是只增不减的**。

- `status` 会从「未扣费」变成「已扣费」
- 退款、取消、补录都可能改动或删除已有记录

所以**绝对不能只追加新记录**。正确做法是：**刷新时整月替换**。

这也意味着"增量"的真实含义是「**只重拉可能变动的月份**」，而不是「只拉新增的那几条」。接口只支持按月查，没有"给我某时间之后的记录"这种能力——想做到真正的时间点增量，得先有服务端支持，而现在没有。

### 4.5 缓存不是权威数据

- 记录页要显示"数据更新于 X"，让人知道看到的是什么时候的
- 缓存命中时，当前月仍在后台刷新，刷完静默更新
- 网络失败时用缓存兜底，但要标注"离线数据"

## 五、工作量与建议顺序

| 步骤 | 内容 | 估算 |
| --- | --- | --- |
| 1 | 翻页拉全 + 「加载更多」按钮 | 小，收益最大 |
| 2 | localStorage 缓存 + 命中直接渲染 | 中 |
| 3 | 按月分级的刷新策略 | 小 |
| 4 | 「清除本地缓存」入口 + 更新隐私说明 | 小 |
| 5 | 记录页下拉刷新 | 小 |

**建议先做第 1 步**：它独立、风险低、立刻解决"看不全"。缓存可以之后单独做，不影响第 1 步的成果。

## 六、不建议做的事

- **不做真正的服务端增量接口**：需要服务端支持"按时间游标查询"，而这条链路的服务端不是我们控制的
- **不在服务端缓存记录**：与无状态模式的承诺直接冲突
- **不做跨设备同步**：那需要账号体系和服务端存储，等于把项目性质改掉
- **不做逐条合并去重**：没有稳定主键，合并规则会越来越复杂，收益抵不上风险
