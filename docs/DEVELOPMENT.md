## 0. 起因：一个非常具体的痛点

校园用水系统里，「洗澡预约」藏在一长串路径后面：

```
打开官方客户端 → 开屏广告 → 首页信息流 → 找到用水入口 → 点洗澡 → 找到预约按钮
```

广告这一条值得单独说说，因为它比「有广告」更糟。

一次实测录屏（52 秒）里数到的顺序是：

```
开屏页（logo + 插画）
  → 广告（蚂蚁阿福助手 / 美团游戏 / 天猫双11，各带「跳过」倒计时）
  → 首页
```

光是这三个广告就占了十几秒。

### 对照实验：三种权限设置各启动一次

同一段录屏里把「设备动作与方向」权限分别设成三档，各启动一次：

| 权限设置 | 启动过程 | 耗时 |
| --- | --- | --- |
| **允许** | 开屏页 → 广告（蚂蚁阿福助手）→ 首页 | 约 7.5 秒 |
| **仅开屏时不允许** | 开屏页 → 广告（美团游戏）→ 首页 | 约 8.5 秒 |
| **不允许** | 开屏页 → 广告（天猫双11）→ 首页 | 约 9.5 秒 |

**三段耗时基本一致，流程也完全一样** —— 结论是：**不论传感器权限设成哪一档，启动都远比系统默认给的 6 秒跳过窗口长**。换句话说，系统自动给的那档「仅开屏时不允许」并不比其它两档快多少，那个 6 秒对它来说是不够用的。

### 顺带发现：这个「跳过」按钮本身就不可靠

逐帧对比三段的广告按钮，能看出两套不同的样式：

| 段 | 按钮 | 倒计时 | 点下去的结果 |
| --- | --- | --- | --- |
| 允许 | 纯文字「跳过」 | 无 | 正常跳过，进入首页 |
| 仅开屏时不允许 | 「跳过 5 → 4 → 3 → 2」 | 有 | **跳进了美团页面**，App 同时提示「进入后台运行」 |
| 不允许 | 纯文字「跳过」 | 无 | 正常跳过，进入首页 |

出问题的是中间那次：**这个带倒计时的「跳过 5 → 4 → 3 → 2」按钮，点下去并没有跳过，而是直接被带去了美团页面**，完美校园自己则提示「进入后台运行」。

也就是说这个按钮**形同虚设**：想跳过的时候未必跳得掉，不想看广告的时候一点就跳到别处去了。

至于为什么这一点就跳走了，**目前无法判断** —— 录屏里 23.5 秒时还停在完美校园开屏页，24 秒广告页出现时内容和按钮都已就位，看不出明显异常，也没有更多证据。（早期把这次记成「这一档会卡住」是当成了必然，实际并不成立 —— 经反复测试确认是**偶发**现象，与权限设置无关。但「跳过」按钮本身不可靠这一点，三段对比下来是清楚的。）

### 再叠一层：切后台回来要重播

只要预约成功后把 App 切到后台几秒钟，再切回来，它会重新播一遍开屏 logo 和广告，之后才回到之前那个预约成功的页面。

也就是说这个广告不是「打开时看一次」，而是**每次从后台回来都要再看一次**。

两层叠在一起：

| | 原版 | 本项目 |
| --- | --- | --- |
| 启动 | 十几秒（开屏页 + 广告 + 跳过窗口不够用） | 直接打开 |
| 切后台再回来 | 重播一遍开屏 + 广告 | 回到原页面 |

对「点开就看验证码」这件事来说，这两下加起来非常难用。

本项目不跟广告 SDK 较劲，直接把这个环节整个去掉 —— 打开就是洗澡页。

另外还有一个长期存在的报错：预约时提示「不能早于当前时间」，手机时间明明正常，却怎么都提交不了。

它的成因不是「手机时间不准」，而是官方把预约开始时间的默认精度从「分钟」改成了「秒」，导致原本 1 分钟的容错窗口被压缩成 1 秒 —— 手速稍慢就必然报错。细节见 3.3.1。

于是定下三个目标：

1. 只保留洗澡与必要信息，去掉开屏广告和复杂首页；
2. 修掉预约时间报错；
3. 尽量不依赖官方客户端、不需要设备高权限。

## 1. 第一回合：先判断「目标代码在哪一层」

最初的想法是分析官方客户端。很快遇到两个现实问题：客户端有代码保护与运行期防护，正面分析的投入产出比很低。

复盘时发现了更关键的一点：**洗澡业务其实是独立的 H5 单页应用，不是原生页面**。也就是说，只要能理解前端的调用方式，就完全不必去处理整个客户端的原生代码。

> 教训一：先判断目标代码到底在哪一层，再决定要不要硬磕。这一步省掉了后面大量无效工作。

---

## 2. 转折点：官方前端静态资源

真正的突破口是：这套业务的脚本、页面结构与交互逻辑，本身就在可以直接访问的静态资源里。

由此拿到三样东西：

- 业务调用的先后顺序与参数结构；
- 页面交互逻辑（包括那个时间报错的来由）；
- 后续所有功能设计的参照物，例如官方的限时/限额档位。

## 3. 协议还原

### 3.1 两类请求

整个业务只依赖两种调用：

```
入口：一次带凭证的跳转请求，服务端在响应里交回后续要用的会话参数
业务：一次参数提交，另外携带会话标识与一个时效性的签名
```

这两处各有一个坑：

- 某个来源标记必须同时出现在两处，少一处服务端就返回空；
- 签名是把会话标识与时间按官方网页里的固定规则算出来的，算法与常量不在本文展开。如果要移植到另一种语言，别自己写「等价实现」，先用同一套库逐字节对齐。

后来在 Java 侧重写时确认：只要输入拼接顺序与输出编码完全对齐，两种语言的实现结果一致。另外前端在页面加载时只算一次签名、后续请求复用，可见它更像格式校验而非严格防重放。

### 3.2 业务命令

| 用途 | 含义 |
| --- | --- |
| 浴室列表 | 拉取可用浴室与空闲数 |
| 预约 / 取消 | 预约、按订单号撤销 |
| 余额 | 单独查账户余额 |
| 限时限额 | 读取与保存消费限制 |
| 记录 | 近几个月用水明细 |
| 用户水控信息 | 账户与设备关联信息 |
| 开阀 | 扫码 / 验证码开阀 |

> 具体命令名见源码 `Api.java` / `vwater.py`。

### 3.3 「不能早于当前时间」的真相

原版前端在组件初始化时把「选中时间」设成打开页面那一刻，提交时再取当前时间比较，只要前者小于后者就抛错。

实测结论：

- 服务端根本不校验预约时间；
- 服务端写入时会强制改写成服务器当前时间；
- 本机时钟与服务端存在十几分钟偏差，前后端一叠加，这个报错几乎必然出现。

所以最终方案不是「校准时间」，而是**结构上取消时间选择**：直接以服务端时间为准提交。报错从此不存在。

#### 3.3.1 这个报错的真实成因：默认入口的容错窗口只有 1 秒

这个报错还有一层更具体的成因，是后来把原版前端脚本逐行读出来才看清的——它**不是单纯的时钟偏差问题**，而是**默认入口取到的时间带着真实秒数**。

原版前端有两条路径会产生「选中时间」，**同一版本里同时存在**：

| 产生方式 | 触发条件 | 时间串格式 |
| --- | --- | --- |
| 组件初始化时直接取当前时间 | **默认进入预约页，不碰时间选择器** | `HH:mm:ss`（秒是真实秒） |
| 时间选择器确认后回填 | 手动打开选择器并选过时间 | `HH:mm:ss`（秒被硬写成 `00`） |

提交时拿这个字符串和「此刻」的 `HH:mm:ss` 做**字符串字典序比较**（同格式下等价于时间比较），小于即报错。于是：

| 走哪条路 | 容错窗口 |
| --- | --- |
| **默认进入**（秒是真实秒） | 只要**过了 1 秒**再点，比较就成立 → 容错 **1 秒** |
| **手动选过时间**（秒恒为 `00`） | 只要在**同一分钟内**点提交，比较不成立 → 容错 **1 分钟** |

也就是说：手动选一次时间，容错就从 1 秒变回 1 分钟——代价是多一步操作。

**默认入口才是绝大多数人踩到的那条**，所以体感上就是「手速稍慢一点，预约必然报『不能早于当前时间』」，而且没有任何提示说明为什么。

至于更早的版本为什么是「1 分钟」：**那次对应的 H5 应该不是从服务器下发的**（具体是哪一套前端无从确认），初步猜测是它取当前时间只精确到分钟。**这只是猜测，没有证据**，此处不做定论。

这里有两点值得记下来：

1. **本机时钟偏差与这个报错无关。** 比较的两端都取自本机 `Date`，时钟快慢不影响判定。真正的原因是同一台设备上两个时间串的秒位不同。（本机快十几分钟是另一条独立的坑，见上文实测结论。）
2. **这是纯前端行为，服务端从头到尾没有参与。** 报错是官方网页自己在本地抛出来的，服务端既不校验也不拒绝。**换句话说，这个报错完全是自己吓自己。**

本项目的做法因此更彻底：既然时间选择本身没有业务意义（验证码当日有效、限时从开阀那一刻起累计），就**不让它出现在界面上**——提交时直接用服务端时间、秒位补 `0`，一次绕开整条比较链路。这样即使官方再改默认值精度，本项目也不受影响。

> 教训：遇到「明明时间正常却报错」这类问题，先分清是**谁在比较、比较的是谁**。这次如果只盯着「本机时钟不准」去校时，会完全找错方向——真正的比较发生在页面里，两端还都是同一个时钟。
>
> 附带收获：默认入口 1 秒、手动选时间 1 分钟这个差异，可以反过来用作**判断手上这个版本走的是哪条路径**的线索；「以前好好的、现在点不动」也可以同时为真——**不是用户变挑剔了，是默认值精度变了。**

### 3.4 业务规则（实测 + 官方文案）

> 以下为**实测学校**的配置，其他学校可能不同，详见 README 的「适用范围与其他学校」。

- 验证码当日有效，可重复使用；
- 限时 / 限额从设备开阀那一刻起累计，超限后重新输入同一个验证码可以再开；
- 预约可以多条并存，取消靠订单号；
- 业务类型区分预约洗澡、热水、宿舍淋浴；
- 限时 1–120 分钟、限额 1–20 元，官方另有「不限额」档；
- **充值无法复刻**：官方支付走微信小程序，校验 `appid + 包名 + 签名` 三者绑定，第三方客户端调不起。最终只做「说明 + 打开微信」。

### 3.5 相对原版多出来的几个能力

原版能做的，本项目基本都做了；下面这几条是**原版做不到、我们能做到**的。它们的性质不完全一样，值的分量也不同。

| 能力 | 原版 | 服务端 | 本项目 |
| --- | --- | --- | --- |
| **星标宿舍楼** | **没有这个概念** | 也没有 | 客户端本地实现：选一栋楼，之后列表只显示这一栋；A/B 区合并为同一栋，某个区设备坏了可去同楼另一区 |
| **限额粒度** | 21 个固定档（1–20 整数元 + 不限额） | 实测**接受小数** | 0.05 元一档共 380 档（滑块 + 文本框） |
| **限时粒度** | 1–10 分钟每分钟一档，之后每 5 分钟一档 | 不涉及 | 1–120 分钟每分钟一档 |

**星标是纯增量。** 把原版前端脚本逐行读完后确认：整个 H5 里**没有任何收藏 / 星标 / 置顶的功能**（`star` 的全部命中都是 `start_opdt`、`startpicker` 这类子串误匹配，`mark` 是设备「备注名」）。原版浴室列表是**平铺渲染**的，没有排序、没有分组、没有收藏，唯一的替代手段是一个**按浴室名到服务端搜**的搜索框 —— 也就是说，想知道自己住哪栋楼，每次都得在几十个浴室里翻或一个个搜。

顺带说明两件容易被混为一谈的事：

- **列表排序也是我们加的。** 原版直接按服务端返回的顺序渲染；我们按宿舍名里的中文数字排（`bathroomcode` 是浴室内部编号，与宿舍号无关，不能拿来排）。
- **搜索是原版唯一的替代手段，而且它并不好用** —— 按「浴室名」搜，不是按「楼栋」搜，且每次都要发一次请求。

星标的实际价值不在于多了一个按钮，而在于**把「找自己那一栋」这件事从每次都要做的动作，变成了配置一次就长期生效的状态**。至于「别的楼门禁根本进不去」这个约束，也就顺带把「只显示同一栋」变成了默认行为。

**限额粒度那一项则是另一种性质**：那 21 个整数档是官方前端自己画的框，服务端并不要求。所以我们按浴室实际的扣费单位（0.05 元）放开，等于**把官方藏起来的能力还给了用户** —— 例如「这次最多洗到 1.50 元就停」，原版选 1 或 2 都做不到。

两者的区别值得记下来：**星标是原版没有的概念，限额粒度是原版前端把它锁死了。** 前者是加法，后者是解锁。

## 4. 第一版：本地服务 + PWA

早期原型是一个零依赖的本地 HTTP 服务，加一个可添加到主屏幕的网页：

| 文件 | 作用 |
| --- | --- |
| `server.py` | 静态页 + JSON 接口 |
| `vwater.py` | 协议封装 |
| `sign.js` | 早期的签名实现（后改为纯 Python） |
| `web/index.html` | PWA 界面 |
| `fetch_token.py` / `refresh.py` | 早期获取与刷新登录态 |

形态是「电脑跑服务，手机浏览器访问网页」。

**局限**：H5 票据短时效，由官方客户端每次打开时重新生成；这一版仍强依赖设备高权限与官方客户端，离目标 3 还很远。

## 5. Android 化：先回答「能不能不靠高权限」

### 5.1 系统级权限方案不可行

尝试过借助系统级权限访问官方客户端的应用数据目录与页面组件，但应用数据目录有隔离、相关组件未导出，几条路都不通；除非直接使用设备最高权限，那本质上还是没摆脱依赖。

### 5.2 妥协方案：WebView 套壳 + Java 重写协议

- 界面 100% 复用 PWA 的 `index.html`，只改请求入口与跳转；
- 协议用 Java 重写（`Api.java`）；
- 早期版本仍需从设备读取官方客户端生成的短票据；
- 产物约 41 KB。

### 5.3 手工构建链路（不装 Gradle / Android Studio）

```
aapt2 compile   编译 res
aapt2 link      链资源与清单，-A assets
javac           编译 Java（含 R.java）
d8              转 classes.dex
python          把 dex 塞进 base.apk
zipalign / apksigner  对齐 + v1/v2/v3 签名
```

SDK 目录命名、平台包版本，以及 javac 编译含 lambda 代码时需要的 `core-lambda-stubs.jar`，都是容易踩的坑；后者的报错还常被脚本里的管道吞掉退出码，容易误判成「编译成功」。

### 5.4 双端可验证的前端

构建脚本从网页版 `index.html` 生成 WebView 版：把 `fetch` 换成原生异步桥、跳转换成原生打开链接、增加返回与票据就绪回调。

关键是：**浏览器里没有原生桥对象时自动回落 `fetch`**，所以能在电脑上用 Playwright 验证 WebView 版界面，不必每次都装真机。

### 5.5 体验设计

- 冷启动先用本地存的票据顶上，不等外部读取；
- 回到前台超过一定时间就自动重读；
- 接口报「登录态失效」时自动重读一次再重试；
- 读取入口加同步，防止冷启动与界面请求并发弹两次授权。

### 5.6 转折点：这个方案本来就不成立

做到这里，卡住的其实不只是技术，还有两个越想越不对劲的地方。

**一是门槛太高。** 要让这套东西跑起来，得先给手机获取 root 权限，普通同学根本不会为了洗个澡去折腾这个。这跟「打开就能用」的初衷正好相反。

**二是这个软件根本没有存在意义。** 短票据是官方客户端生成的，过几十分钟就失效，所以每隔一阵还得**打开一次原来的软件**，让它把票据刷新出来，这边才能接着用。可要是都得打开原版软件了，那做这个软件图什么呢？开屏广告也看了，首页也翻了，最烦的那几步一步都没省掉。

> 想明白这一点，方向就变了：**只要还依赖原版软件给票据，这个工具就不值得做。**

于是问题从「怎么更方便地把票据拿过来」，换成「怎么自己登录、自己拿到一张能用的票据」。下一章就是这件事。

## 6. 独立登录：彻底摆脱额外依赖

这是整个项目最关键的一次转向。

### 6.1 关键推导

参考公开的登录协议实现，并对照官方前端，梳理出会话凭据的生成链路：**H5 使用的凭据与登录会话是同一份**，而且必须在同一个会话内按固定顺序完成「建立会话 → 短信验证」，它才会升格为账号会话。

### 6.2 方案成立

于是「纯登录」方案成立：客户端自己用手机号 + 短信验证码登录，设备高权限和官方客户端都不再需要。这也是从「网页原型」变成「可独立分发的 App」的分水岭。

### 6.3 登录实现与踩坑

`Login.java` 把整套登录流程实现了一遍：建立会话、加密参数、计算签名，三步缺一不可。

- 公钥的编码格式必须与服务端期望的完全一致；换成另一种常见编码，服务端会返回 200 + 空响应，极难排查；
- 余额不能复用浴室列表里那个占位字段（恒为 0），必须单独查；
- 学校名字段带下划线后缀，容易漏；
- 浴室排序键在宿舍名称里的中文数字里，浴室内部编号与宿舍号无关，不能拿来排序；
- 星标状态存原生 `SharedPreferences`（`file://` 页面里 `localStorage` 不可靠）。

## 6.4 大白话版：从「能登录」到「能查到洗澡信息」，中间还差什么

这一节不写代码，专门讲清楚整个项目最关键的一步。

**先说结论**：开源的登录实现只帮你办好了「证明我是我」这件事；而洗澡系统要的是「证明完身份之后，还能按它的规矩继续对话」。中间差的那一截，就是下面要讲的。

### 打个比方

把整套系统想成一栋宿舍楼：

- 开源的登录实现 = **在门口办了一张门禁卡**。它教你怎么用手机号和短信验证码换到这张卡，做完就结束了 —— 那些开源项目本来是用来签到、打卡的，证明身份就够了。
- 但洗澡的地方不认门禁卡本身。你得先拿卡去**前台换一张「洗澡牌」**，前台还会顺便登记你是哪个学校、哪个学号。
- 之后每次跟窗口说话，都要**按一个固定暗号报出时间和牌号**，说错一点对方就不理你。
- 而且这张洗澡牌**过一阵就作废**，得重新去前台换。

所以「登录成功」和「能看到浴室列表」之间，还隔着三件事。

### 第一件：把登录拿到的资料填对地方

登录成功后，服务器会回一堆资料：姓名、学号、学校编号、手机号，还有几个长得很像的编号。问题是，**洗澡那边要填的表格，栏目名和登录给的对不上**。

比如登录给你的叫「客户编号」，洗澡前台要的叫「学校码」；登录给的是「一卡通客户号」，洗澡要的是另一个字段；学号也有好几个候选，得挑对那个。

填错一个，前台就直接不给换牌 —— 表现出来就是「明明登录成功了，一打开浴室列表却说登录态失效」。这一步没什么高深技巧，就是一个个对着官方网页试出来的对照表，外加一条规矩：**前台重新发回来的身份参数，以它的为准**，别固执地用自己登录时拿到的值。

### 第二件：拿卡去前台换「洗澡牌」

办完卡不能直接去洗澡，得先访问一个「入口」。带上刚才填好的资料和门禁卡，服务器会做一次跳转，在跳转地址里塞回来两样东西：

- 一个**牌号**（后面每次请求都要带着它）；
- 服务端重新确认过的学校码、学号等身份参数。

还有两个小细节：牌号会过期，所以要记住「上次换牌是什么时候」，太久就再换一次；万一对方说牌作废了，也要能自动重换再重试。这两条不做，用着用着就会突然「掉登录」。

### 第三件：学会那套「报暗号」的规矩

换到牌之后，每次问事情（查浴室、预约、查余额、改限额、看记录）都要按同一套格式说话：

- 说明要办什么事；
- 带上牌号；
- 带上当前的毫秒时间；
- 再按官方网页里那套规则，把「牌号 + 时间」算成一个**签名**一起发过去。

少带一样、顺序写反、或者时间格式不对，服务器要么不理你，要么回个空结果。这套规矩不在任何开源登录项目里，是从官方洗澡网页自己的脚本里读出来，再在电脑版和手机版里各做一遍、两边结果逐字节对上才算数的。

另外还有两个小坑：**余额别信浴室列表里那个数**（它永远是 0，只是个占位，得单独问一次）；**时间别用手机自己的钟**（~~我们的手机比服务器快了十几分钟~~，所以干脆不让人选时间，直接用服务器的时间）。

> **订正（2026-11-11）**：「我们的手机比服务器快了十几分钟」这句**是错的**，保留原文是为了标记错误源头。
>
> 它来自开发早期一次**无效测量**：把接口返回的 `nowdate`（某一瞬间的快照）和当时仍在走动的开发机时钟相减，得到的差值会随时间流逝一起变大，根本不是时钟偏差。两次采样从 −487 秒涨到 −887 秒、涨了 400 秒（约 6.7 分钟），正是两次操作之间的真实间隔——当时已经注意到「服务端只走了 30 秒，本地却走了 8 分钟」这个矛盾，却用「两次调用间隔确实是 8 分钟」把它解释过去，没有意识到这恰好证明测的不是时钟差。
>
> 而且**测的是开发机，不是手机**，结论却记到了手机头上。手机一直与北京时间同步。
>
> 真正偏的是校内**水控器**（曾慢约 15 分钟）。「15 分钟」这个数字纯属巧合：无效测量碰上水控器当时真实的误差，两个不相干的数撞成了同一个，于是这个错误结论看起来被「印证」了。完整过程见 [第 11 节「时钟误差研究过程」](#11-时钟误差研究过程留给未来的记录)。

### 那这一步到底解决了什么？

早期版本一直有个很别扭的地方：洗澡网页用的那张「通行证」是官方 App 每次打开时临时生成的，寿命只有几十分钟。所以第一版只能靠设备高权限，隔一会儿就去官方 App 里把新通行证捞出来 —— 又麻烦，又离不开官方 App。

后来才想明白一件事：**登录时办的那张门禁卡，和洗澡网页要的通行证，本来就是同一张卡**。只要从头到尾用同一个会话，按「先跟服务器对好一次暗号、再提交短信验证码」的顺序走完，这张卡就会自动升格成能用的通行证，不需要再去别处捞。

想通这一点之后：

- 不用设备高权限了；
- 不用装官方 App 了；
- 打开自己的客户端，输手机号和验证码，就能直接看到浴室列表和余额。

**所以这一步不是「又多写了一个接口」，而是把「登录」和「洗澡」这两件原本被拼在一起的事，用同一张卡串了起来。** 前面那些填表、换牌、报暗号的活儿，都是为了让这张卡在洗澡系统里真的被认。

## 7. 工程化：审计、分仓、发布

### 7.1 隐私审计

结论：**安装包干净**。界面、协议代码、图标里没有任何个人信息、票据、学校名或手机号。

运行期才会产生敏感数据：应用私有目录的 `shared_prefs` 里存会话、姓名、学号、手机号；已设 `allowBackup=false`，其他应用读不到。

自检脚本 `tools/audit_apk.py` 用通用正则（手机号 / UUID / 长十六进制 / 学校字样）+ 权限与组件检查，也支持 `--config` 补真实值逐字比对。建议每次打包后都跑一次。

### 7.2 分成两个仓库

```
wanmei-bath-android/   Manifest + src(4 个 Java) + res + assets/index.html + tools/
wanmei-bath-web/       server.py / vwater.py / wxlogin.py / login.py / web/ + config.example.json
```

网页端把签名从「调 Node 跑 `sign.js`」改成**纯 Python**（pycryptodome），与 Node 输出逐字节比对一致，从此不再需要 Node.js。

`.gitignore` 排除 `config.json` / keystore / build；`.gitattributes` 保证 `*.sh` 为 LF。

### 7.3 Git 与 Release

- 提交作者用 `git rebase` 配合 `--reset-author` 统一重写，再以 `push --force-with-lease` 推送；
- **git 命令只能打 tag，不能创建 Release**。Release 是平台对象，需要网页、`gh` 或 REST API；tag 只是指向提交的引用；
- 三个版本的 Release 均已创建并上传 APK 资产，发布说明取自仓库内的发布说明文档。

**功能**

**两个回归 bug**

1. **验证码卡片串页**：定时刷新没有判断弹层是否打开，而渲染函数无条件清除 `hidden`；tab 切换恰恰靠 `hidden` 隐藏首页卡片。修复：定时器跳过打开的弹层，渲染函数按当前 tab 决定显示。
   > 教训二：显示状态要收敛到渲染函数里按当前状态计算，别分散在「切换时设隐藏」和「渲染时无条件清除」。
2. **遮罩残留导致整页点不动**：给关闭函数加状态清理时，用精确字符串补丁误删了移除遮罩 class 的那一行，遮罩永远保留激活态。修复：抽出 `closeMask()` 显式移除 class + inline 强制关闭，并加 400 ms 自愈巡检。
   > 教训三：精确字符串替换的 old / new 必须覆盖完整函数体，改完一定要复核 diff；这次是靠真机截图 + 重读源码才定位。

### 8.4 1.0.3（检查更新）

「检查更新」是最容易做成「点一下转圈然后失败」的功能，原因是它天然依赖 GitHub —— 而 GitHub 在国内经常打不开。所以这次的核心不是加一个按钮，而是**给「检测失败」设计一条完整的退路**。

**检测通道（并行探测，先成功先用）**

| 通道 | 内容 | 特点 |
| --- | --- | --- |
| GitHub 官方 API | `api.github.com/.../releases/latest` | 唯一能拿到更新日志、APK 直链与 `digest`（sha256）的来源；但国内时通时不通 |
| jsDelivr CDN | 读仓库里的 `latest.json` | 国内 CDN 稳，但内容是自己维护的清单，可能落后于真实发布 |
| raw 直连 | `raw.githubusercontent.com` | 最后一搏，通常也不通 |
| **APK 内置清单** | `assets/latest.json` | 零网络依赖，断网也知道「最新是哪个版本、去哪下」 |
| **上次缓存** | SharedPreferences / 服务端 `version_cache.json` | 全部通道失败时至少能报出上次看到的版本 |

> 实测（2026-11）：官方 API 与 jsDelivr 三个节点可达；raw 直连时通时不通。
>
> **曾经这里还有一条 `ghproxy.cn` 的代理镜像，1.0.4 已彻底删除。** 在移动网络下实测，该域名会把下载请求跳转到色情网站。这类免费代理域名随时可能被抢注或劫持，把用户导向哪里完全不受我们控制——当时为了「多一条通道」引入它，是个不该犯的错：**通道数量带来的收益，远小于把用户交给一个不受控域名所承担的风险。**
>
> 现在的原则是：**只使用有企业背书的 CDN**（jsDelivr 三节点）。APK 同时提交到仓库 `release/` 目录供 CDN 分发——Release 资产 CDN 取不到，只有仓库文件可以。文件名带版本号，每版路径都是新的，所以分支缓存不会让用户拿到旧文件。

**撤回 1.0.3（2026-11-10）**

1.0.3 是第一个带「检查更新」的版本。它把两个免费 GitHub 加速代理（`ghfast.top`、`ghproxy.cn`）写进了下载镜像，理由是「GitHub 直连太不稳，多一条通道总是好的」。

这个判断错在两个地方：

1. **免费代理域名不受控**。它们可能被抢注、被劫持，把你用户导向哪里完全由别人决定。事实是 `ghproxy.cn` 在移动网络下已经会跳转到色情网站。
2. **风险与收益不对称**。多一条通道的收益是「偶尔能下」，代价是「可能把用户送到任意站点」。这条根本不值得换。

处理：删除 Release、删除 tag、删除仓库内的安装包，`@v1.0.3` 路径已 404。

但有一件事必须承认：**已经装在手机上的 1.0.3 救不回来**。那些域名是写死在代码里的，服务端返回什么数据都改变不了它的行为——它照样会在弹层里列出那两个链接，等用户去点。唯一的补救是让用户升级，并明确告诉他别点。

这也说明一件事：**涉及第三方域名的决策，一旦发出就几乎无法收回。** 发布前的检查比发布后的补救重要得多。

**发版纪律（踩过坑才补上的）**

> **发布前必须获得用户明确同意。** 开发完成不等于可以发布——打 tag、发 Release、推到公开渠道都是不可逆动作，要先问过用户、得到点头才做。
> 可以直接做的：本地构建、测试、提交到本地仓库、产出待发布包（如 `zhishui-1.1.x-test.apk`）。这些都可逆。
> 之所以单列一条：自动化流程一旦跑通，很容易把「最后一步」顺手做完，而发版时机是用户的判断，不是流程的一部分。

0. **加速地址一律用 `@v<version>`，不要用 `@main`。**
   jsDelivr 对整个分支快照有最长 12 小时的**解析**缓存。刚发版时 `@main` 可能仍指向旧提交，表现为新文件 404、或返回上一版内容。`purge.jsdelivr.net` 清得掉边缘缓存，但清不掉这层解析缓存（实测连 purge 三次、等 30 秒，三个节点仍返回旧快照）。
   每个版本的 tag 是全新引用，没有任何缓存，立刻可用。**代价是发版顺序被锁死：提交 APK → 打 tag → 发 Release**，tag 里没有 APK 就会 404。
1. **同一个版本号的文件，发布后不要再替换。** 要改就升版本号。
   jsDelivr 按 URL 缓存，同名文件换内容后，旧字节会继续被返回。真要替换，先验证 `@<commit>` 已能拿到新内容，再换资产。
2. 发布前用三个节点各下一次，把 SHA-256 与本地逐字节比对。**只验证一个节点不够**，它们回源时机不同。
3. 一定要替换资产时，先用 `@<commit>` 验证新内容已在 CDN 就位，再替换 Release 资产，否则会出现「Release 的 digest 与 CDN 文件不一致」——用户按弹层里的 SHA 校验会失败。

**几个决定**

- **官方 API 的结果优先于清单文件**：清单是手写的，可能忘记更新；两者都拿到时取版本号更高的那个，避免展示比已知更旧的版本。
- **失败也要给出下载入口**：弹层里直链、两个镜像、项目主页永远在，只是标明来自「上次检测结果 / 内置清单」，并如实列出「已尝试的通道」。
- **APK 自带清单**：把 `latest.json` 打进 APK，`Update.java` 直接读 assets。这样「完全断网」的用户也能拿到下载地址，而不是看到一个空白弹窗。
- **一键下载**：走系统 `DownloadManager`，不指定保存目录（落在系统共享下载缓存，由通知引导安装），因此**不需要新增任何存储权限**；同时保留系统浏览器打开作为备选。
- **版本比较按字符串语义**：不是整数比大小 —— `1.0.10 > 1.0.9`，`1.0.3-dev < 1.0.3`。Java 与 JS 两端各写了一份，规则必须一致，所以用同一组用例在两边跑同一批断言（8 组全过）。
- **网页端不比较版本**：网页刷新就是最新，「检查更新」在这里的意义是顺带给出 Android 客户端的最新版，所以状态文案是「网页端无需安装」，并提供「刷新页面」。
- **服务端代查**：网页端的 `/api/version` 由服务端去查 GitHub（服务端所在网络通常比用户手机更通），查不到再退回随包发布的 `web/latest.json`；降级结果只缓存 5 分钟，网络恢复后尽快重探。

> 教训五：做依赖外部服务的功能，先想清楚「它不通的时候长什么样」。把降级路径当成主流程的一部分来设计，而不是事后补丁。

## 9. 验证体系

整个项目没有靠「看起来没问题」交付，而是分层验证：

**静态**：`node --check` 检查抽出的脚本、扫描所有 DOM id 引用确认存在、`git diff --check` 检查空白错误。

**浏览器（Playwright）**：覆盖请求层做 mock，测批量取消预约、星标筛选、登录失效提示；用 `TouchEvent` 模拟下拉刷新与弹层拖动；多视口测量布局是否居中、溢出；测几何要等弹层动画结束，否则量到的是过渡中间态，会误判按钮被裁切。

**真机（ADB）**：覆盖安装 → 强停 → 重新启动 → 截图核对；必要时唤醒屏幕，避免截到全黑帧。

**打包自检**：APK 内不含个人信息；`apksigner verify` 确认签名方案（`jarsigner` 复核 v1，minSdk 26 时 v1 显示 false 属正常）；一直复用同一签名证书，保证所有版本可直接覆盖安装。

1. 先确认业务在哪一层，别在不必要的方向上硬磕；

## 11. 时钟误差研究过程

这一节记录一件被搞错、又被纠正的事。留档的原因很实际：**观察窗口已经关闭，将来无法重新测量**，所以过程本身是唯一的证据。

### 11.1 可靠的部分：多年观察到的现象

这两个事实来自使用者的长期观察，不是推断：

- **过了北京时间的 0 点，预约不会马上失效**，要再过十几分钟才失效；
- 群里的其他人也遇到过同样情况，2026-11-11 零点再次出现。

「零点过后还能用」这一点反复出现、跨人跨年，可以当真。但它只说明**有个时钟比北京时间偏慢约十几分钟**，不说明是哪一个。

### 11.2 出错的部分：把偏差安到了云端服务器上

开发早期做过一次「测时钟偏差」，得到 −487 秒后改判为 −887 秒，于是认定「本地比服务器快 15 分钟」，并写进文档传播。

**这次测量从一开始就是无效的**，原因有两层：

**第一层，减法的两端不同步。**

用的是接口返回的 `nowdate`（格式 `HHMMSS`，某一瞬间的快照）减去当时仍在走动的开发机时钟：

```
偏差 = nowdate(瞬间快照) − 本机当前时刻(持续在走)
```

前一次测量得 −487 秒（服务端 15:47、本机显示 15:55），后一次得 −887 秒（服务端 15:48、本机 16:03）。当时已经察觉到矛盾，原话是「**服务端只走了 30 秒，本地却走了 8 分钟**」「如果本地时钟真的快 15 分钟，偏差应该稳定」——这个直觉是对的。

但下一步推错了：它把矛盾解释成「两次调用之间我确实做了很多事，间隔就是 8 分钟」，于是认定「pc 时间恒定快 15 分钟」。**实际上那 8 分钟正是两次操作的真实间隔，而它恰恰证明了测的不是时钟差。**

道理很简单：如果两端测的是同一时刻，那不管隔多久再测，差值都应该恒定。差值随时间增长，只能说有一端没跟着时间走——`nowdate` 是几分钟前那个瞬间的快照，它不会前进，本机时钟却一直在前进。

**差值漂移本身就是这次测量无效的证据，当时却把它读成了「时钟恒定偏快」的佐证。**

**第二层，测错了对象。**

测量跑在开发机上（Playwright / Python 本机进程，取的是 Windows 系统时间）。得到结论后写成的是「**我们的手机**比服务器快了十几分钟」——手机从头到尾没有被测过。而使用者明确说明：手机时间一直与北京时间同步。

### 11.3 「15 分钟」这个数字是巧合

这是整件事最容易骗人的地方：无效测量得出的 15 分钟，**恰好等于**水控器当时真实的偏差。

两个互不相关的量撞成同一个数，于是这个错误结论看起来被现象「印证」了——「零点多能用十几分钟」和「手机快 15 分钟」互相解释得通。错误的因果链就此闭合，之后在两份文档里被反复引用，还被整理成一张看起来很正式的验证表（那张表的输入其实全是假定值，见 [API.md H.7](API.md)）。

**如果当时那个数字是 8 分钟（第一次测量的结果），它和水控器的 15 分钟对不上，这个错误大概当场就会被发现。**

### 11.4 纠正：云端时钟实测是准的

2026-11-11 用 HTTP `Date` 响应头直接测云端时钟。`Date` 是 HTTP 规范要求每个响应都带的头，且实测确认它来自应用容器本身、不是网关改写（对一个不存在的路径发请求，返回的是带 `JSESSIONID` 的 JSON 错误页，`Date` 照样存在）。

| 测量方式 | 偏差 |
| --- | --- |
| 服务端 `Date` 头 vs 北京时间（三次，RTT 34 ms） | −143 / −382 / −418 ms |
| App 内探测（用户设备，含网络单程延迟） | −570 ms |

**云端服务器时钟是准的，亚秒级。** 十几分钟的偏差不在它身上。

### 11.5 窗口关闭

2026-11-11 下午，水控器的时间被**人为调整成了正确的北京时间**。原因不明——没有接到通知，也不清楚是报修、还是管理员自己注意到，这里不写推测。

结果是：**这个偏差再也无法复现、无法测量了。** 上述历史观察就是全部证据，没有补充机会。

### 11.6 结论与遗留前提

- **能不能开阀**由**水控器**判定（校内设备，本地时钟，很可能离线记账，不实时查云端）；
- **能不能下单、订单号是什么**由**云端平台**决定；
- **App 显示什么**由云端时间推算。

三者不是同一个时钟。我们的日切点算法用云端时间推算，**只在水控器时钟正确时才等于设备的真实日切点**。这个前提无法从客户端测量——没有任何接口能读到水控器的时间。

### 11.7 将来再出现「过了 0 点还能用」怎么查

按这个顺序，不要重犯当年的错误：

1. **先怀疑水控器**，不要怀疑云端服务器——云端已实测为准，如需复测用 `Date` 头（几分钟就能确认）；
2. **不要用「快照减当前时刻」测偏差**。要么两端都是同一瞬间的快照（如 `Date` 头 + 收到响应的本机时刻），要么两端都持续计时。混合两者必然得出随时间增长的假偏差；
3. **确认被测对象**：测的是手机就写手机，测的是开发机就不要写成手机；
4. **数字对得上不等于因果成立**。若新测出的偏差和水控器的偏差「正好一致」，先当成巧合排查，别急着下结论。

### 11.8 时间线

| 时间 | 事件 |
| --- | --- |
| 2024 秋 – 2026 秋 | 使用者与群友多次观察到「过 0 点预约不失效」，持续两年多 |
| 开发早期 | 无效测量得出「本机快 15 分钟」，写进文档（手机从未被测） |

#### 「上岛」有三条路，我们走的是第三条

| 路径 | 是否需要资质 | 是否可用 |
| --- | --- | --- |
| 厂商私有 SDK（OPPO 流体云 / 小米焦点通知 / 华为实况窗 / vivo 原子岛） | 要开发者资质 + **签名证书白名单** | ❌ 个人自签名包接不进去 |
| Root Hook 修改系统 | 要 root | ❌ 与「不折腾用户设备」的原则冲突 |
| **Android 16 原生 Live Updates（API 36）** | **都不要** | ✅ 本项目的做法 |

第三条路的原理：应用按**标准**发一条「持续进行中」的通知，**由系统决定渲染成什么形态**。ROM 若兼容这套标准（ColorOS 16 起流体云已接入 Google 标准、HyperOS 超级岛被社区确认支持），系统会自动把它提升成岛/云/窗；不兼容就退化成普通常驻通知。所以不需要向任何厂商申请。

> 早期版本曾断言「只有厂商白名单这条路」，那是错的——漏了这条官方标准通路。InstallerX-Revived 等开源项目走的正是它。

**踩过的坑（重要）**：第一版用 `IMPORTANCE_LOW`，在系统设置的「子类别」里被归成**静默通知**——静默通知不展开、不点亮锁屏，这功能等于没做。而**通道的重要级别一旦创建就无法由程序修改**（系统不允许覆盖用户设置），所以必须换一个新通道 id（`bath_code` → `bath_code_v2`）重建，并在建新通道时删掉旧的。现在用 `IMPORTANCE_DEFAULT`。

厂商的「静默通知」开关没有公开 API，`notifyStatus()` 只能用 `importance <= IMPORTANCE_LOW` 近似判断。所以 App 里给了一块可关闭的提示，把该改的四处写清楚：允许通知 / 锁屏显示通知 / 子类别「验证码显示」关静默 / 同一子类别打开锁屏显示。

**「去设置」故意停在应用级通知页，不直达子类别**：母类一旦关掉「允许通知」或「锁屏显示通知」，子类别里的开关会被系统**隐藏或置灰**，用户跳进去反而改不了，卡在死路上。所以先让用户在母类把父级开关打开，再自己往下点「验证码显示」。

### 12.2 流体云始终不出现：一次「把结果当请求」的误判（1.1.3.10）

**现象**：1.1.3.9 装上后，系统设置里出现了「流体云显示实时活动」开关，首页也显示「系统报告支持实时通知」，但通知栏里仍是传统常驻通知，状态栏胶囊 / 流体云没有出现。

**排查顺序**（每一步都找可复核的证据，不靠猜）：

| 步骤 | 查了什么 | 结论 |
| --- | --- | --- |
| 1 | 拆 1.1.3.9 的清单与 dex | 权限已声明、`applyLiveUpdateFlavor` 确实进了 dex，不是「改了源码忘了同步」 |
| 2 | AOSP `NotificationManagerService` 发通知处的判定 | 只有 `canBePromoted(pkg,uid)` 且 `hasPromotableCharacteristics()` 且通道 importance 大于 `IMPORTANCE_MIN` 时，系统才会给通知打 `FLAG_PROMOTED_ONGOING` |
| 3 | 应用能不能自己设这个 flag | **不能**。`fixNotification` 里明确写着 `notification.flags &= ~FLAG_PROMOTED_ONGOING; // Apps cannot set this flag` |
| 4 | 官方《创建实时更新通知》（Android 16 QPR1） | 必须用 `EXTRA_REQUEST_PROMOTED_ONGOING` 或 `NotificationCompat.Builder#setRequestPromotedOngoing` **请求**提升；且**不得** `setColorized(true)` |
| 5 | 实机能上岛的参照实现：InstallerX-Revived `ModernNotificationBuilder.kt` | `.setRequestPromotedOngoing(true)` + `ProgressStyle`（带段）+ `setShortCriticalText`，既没设 colorized，也没手设 flag |

**根因**：我们把「系统打的结果标记」当成了「应用发出的请求」。

> ~~给通知设 `FLAG_PROMOTED_ONGOING` = 请求提升~~ → **错**。那个位是系统给合格通知打的**结果**，应用设了会被系统清掉。真正缺的是 `android.requestPromotedOngoing=true`；没有它，系统根本不认为这条通知请求过提升，于是永远走传统通知。
>
> ~~首页显示「系统报告支持实时通知」说明已经上岛~~ → **错**。`canPostPromotedNotifications()` 问的是「用户开关有没有允许本应用发提升通知」，既不代表系统支持，也不代表这条通知已被提升。前端已改为只报读回的真实结果。

**一套判定，两个版本**（这个坑值得记牢）：

- AOSP `android16-release` 与 `main` 分支里的 `hasPromotableCharacteristics()` 仍写着 `isColorizedRequested() && ...`，是 QPR1 **之前**的旧判定；
- Android 16 QPR1 起改成 `EXTRA_REQUEST_PROMOTED_ONGOING`，并明确禁止 `setColorized(true)`。
- 所以 1.1.3.8 按旧分支源码加 `setColorized(true)`、1.1.3.9 按官方文档删掉，两次都不算瞎改，但都没补上真正缺的那个 extra。以「官方文档 + 实机能上岛的实现」为准：**写 `android.requestPromotedOngoing=true`，不设 colorized**。

**1.1.3.10 的改动**：

1. `applyLiveUpdateFlavor()` 用 `b.getExtras().putBoolean("android.requestPromotedOngoing", true)` 请求提升（`Builder.build()` 会把 `getExtras()` 合并进 `Notification.extras`，已在 AOSP 源码确认）；平台若有 `setRequestPromotedOngoing(boolean)` 再反射调一次作双保险。`setShortCriticalText` 也改成方法 + extras 双写兜底。~~平台没有这个方法，那只是 AndroidX 的封装~~ → **这句判断错了**：AOSP `android16-qpr1-release` 的 `Notification.java:5555` 确有 `public Builder setRequestPromotedOngoing(boolean)`，只是当时用的 `platform-36 rev2` public SDK 未收录（见 12.6）。
2. 手设 `FLAG_PROMOTED_ONGOING` 降级为「兼容少数直接读 flag 的 ROM」，注释写明它按规范会被清掉。
3. `notifyStatus()` 增加 `diag`：读回自己那条通知的 `found / req / short / style / colorized / chars / flagged / flags / canPost`。前端据此分四种情况给文案，不再用探测结果冒充结论。
4. 新增桥 `openPromotedSettings()`：优先 `android.settings.APP_NOTIFICATION_PROMOTION_SETTINGS`（AOSP 常量名），退而求其次 `android.settings.MANAGE_APP_PROMOTED_NOTIFICATIONS`（文档写法），都不存在就回应用通知总设置页。~~这个独立入口保留下来~~——**1.1.3.12 已删除**，理由见 12.4：它和「去设置」实际落到同一页。
5. 提示框补第 ⑤ 步「流体云显示实时活动」开关，并加「实时活动」直达按钮；诊断显示「通知合格但用户开关没开」时，即使点过「知道了」也会继续提示，避免又卡在没人提醒的地方。
6. 版本号按约定留在 1.1.3.x：**1.1.3.10 / versionCode 21**，不发 1.1.4。

**怎么验证这次是不是真成了**：装 1.1.3.10（签名指纹与线上一致，可直接覆盖安装）→ 有预约时下拉刷新一次让通知重发 → 看提示框里的「实时活动」一行：

- 「已生效 ✓」= 系统确实给通知打了提升标记；
- 「已满足系统条件但没被提升 / 开关没开」= 点「实时活动」打开开关，再刷新一次；
- 「不满足条件」= 括号里会给出 `请求提升` 与 `样式` 的实际读回值，可直接据此定位，不用再来回猜。

**构建附注**：本机 Git Bash 下 `build/build.sh` 原来把 `/c/...` 路径直接写进 javac / d8 的 `@argfile`。MSYS 会自动转换命令行参数，但不会转换列表文件内容，Windows 版 javac 会把它读成 `\c\...` 并报「找不到文件」。已改为用 `cygpath -m -f -` 逐行转换 `sources.txt` / `classes.txt`，并把 `-bootclasspath` / `-classpath` / `--lib` 一并转成 Windows 路径。

### 12.3 上岛之后的格式清理：删倒计时、删进度条（1.1.3.11）

1.1.3.10 在真机上确认流体云已经出现。用户随即提出两处格式问题：普通通知和实时卡片里都有一串看不懂的 `HH:MM:SS`，卡片下面还有一条没有含义的进度条；希望验证码像系统自带的「取单码提醒」那样——一个图标加一个大号数字，旁边什么都没有。

**两处多余元素的来源**

| 现象 | 来源 | 处理 |
| --- | --- | --- |
| 普通通知头部、实时卡片上的 `HH:MM:SS` | `setUsesChronometer(true)` + `setChronometerCountDown(true)` + `setWhen(失效时刻)` | 三个调用全删，改 `setShowWhen(false)` |
| 卡片下方的进度条 | `ProgressStyle` + `addProgressSegment` + `setStyledByProgress(true)` | 整个样式换成 `BigTextStyle` |

- `setWhen()` 传的是当天失效时刻（往往还有十几个小时），这串倒计时对用户没有任何意义。
- 还要显式关 `showWhen`：AndroidX `setShortCriticalText()` 的 javadoc 写明芯片文案的兜底顺序是 `shortCriticalText` → `MetricStyle` 关键指标 → `Notification.when` 的时间（chronometer 优先）。只要 `when` 还是未来时间且 `showWhen=true`，ROM 就仍有理由把倒计时画进芯片。删 chronometer 而不关 showWhen，等于只关了一半。
- `setTimeoutAfter(left)` 保留：AOSP 里 `mTimeout` 只是给 `NotificationManagerService` 排一个自动取消的定时任务（`getTimeoutAfter()` 在 NMS 里只被 8801 / 10269 附近引用），不产生任何可见文字。

**为什么「放大数字」不能靠应用自己加 span**：`Notification.safeCharSequence()` 最后一步是 `removeTextSizeSpans()`，平台会主动剥掉 `RelativeSizeSpan` / `AbsoluteSizeSpan`（并对 `TextAppearanceSpan` 抹掉字号）；`StyleSpan(BOLD)` 能留下，但改不了字号。也就是说第三方应用**不能**自己把验证码画成示例里那种超大数字——那是系统「取单码提醒」私有卡片的排版。

能控制的是「哪个字段最显眼」：`shortCriticalText`（状态栏芯片）、`contentTitle`、`BigTextStyle.setBigContentTitle()`（通知标题与展开后的大标题）全部放验证码，副行只留浴室名。去掉进度样式后系统会走**文本类**实时卡片，正是示例那种「图标 + 数字」的形态。~~给标题套 `RelativeSizeSpan` 就能放大验证码~~——这个想法在第一版实现时被提出来，查 `safeCharSequence()` 后否掉了，平台会直接丢掉该 span。

**换样式会不会失去被提升的资格**：不会。AOSP `Notification.hasPromotableStyle()` 对 `null`（Standard）、`BigTextStyle`、`CallStyle`、`ProgressStyle`、`BigPictureStyle` 都返回 `true`，`BigTextStyle` 在白名单内；`EXTRA_REQUEST_PROMOTED_ONGOING`、`POST_PROMOTED_NOTIFICATIONS`、`ongoing`、`contentTitle` 这些条件一个没动。

**顺带补的诊断**：`notifyStatus().diag` 增加 `showWhen` / `chron`（读 `android.showWhen`、`android.showChronometer` 两个公开 extras 键），提示框加一行紧凑读回「胶囊「…」· 倒计时关 · 时间显示关 · 样式 BigTextStyle」，便于不接 adb 也能确认倒计时源确实关掉了。`audit_apk.py` 仍会报 `assets/index.html` 含「学校名 / 实测本校区」模式——那是第 11 节正文里的句子，1.1.3.10 起就是这个告警，属既有的模式误报。

**版本**：按约定继续留在 1.1.3.x，**1.1.3.11 / versionCode 22**。仅本地提交，未打 tag、未推送、未发布。

### 12.5 退出契约：关掉「允许通知」就是用户的决定（1.1.3.13）

起因是一句只在代码注释里出现过的话：「码会明文显示在锁屏上，室友拿到手机也能看到……风险有限」。把风险判断写进注释、用户却看不见，等于**替对方做了决定**。上一轮讨论后，用户提出的思路是：不想要的人直接关掉通知权限即可，不需要 App 再造一个专用开关。

**真机实测（ColorOS / Android 16，2026-11-12）**：关掉应用级「允许通知」之后，该页下面所有选项都不再显示，**包括「流体云显示实时活动」开关本身**；流体云也随之消失。也就是说：

| 用户能动的开关 | 对流体云是否有效 |
| --- | --- |
| 锁屏显示通知 / 隐藏敏感内容 / 静默通知（细项） | 无效：`VISIBILITY_PUBLIC` 与实时活动都会绕过 |
| 流体云显示实时活动 / 实时动态 | 部分有效：只挡上岛，普通通知仍在 |
| **应用级「允许通知」/ POST_NOTIFICATIONS** | **有效，且是唯一彻底的总闸** |

这条总闸由系统提供，语义无歧义，关掉后子项自动隐藏——**App 再加一层「锁屏显示验证码」开关反而会制造歧义**（关了它流体云还在怎么办），所以不加。这也再次印证 12.4 把「去设置」停在母类通知页是对的。

**改动**：

1. `notifySetupHint()` 不再把「权限没给 / 实时活动开关没开」算成硬错误。原逻辑 `hard = perm === false || switchOff` 会在用户**刚关掉总闸**时反复弹提示框劝他打开，是全项目里最明显的一处「不尊重用户决定」。现在 `dismissed` 一律生效；`perm === false || enabled === false` 时连提示框都不出现（后者覆盖 Android 8~12 没有运行时权限、只能在系统设置里关总闸的情形）。`switchOff` 与劝开权限的 `permLine` 一并删除。
2. **「我的」页新增「验证码显示」分区**：一行静态状态（`已关闭 / 已生效 / 未开启`）+ 点击跳应用通知设置页。复用 `notifyStatus()` 与 `openNotifySettings()`，**没有新增原生桥**。关掉总闸后系统子项全隐藏、提示框也不显示，App 内只剩这一条路能让用户找回来——不弹、不催，但不把路堵死。
3. 把「明文显示」的告知从代码注释挪到用户可见处：「我的」页的静态说明 + 首次提示框（实时活动与老设备两条路径都补了）。文案只陈述事实和撤回方式，删掉「风险有限」这类由代码替用户下的结论，并写明「关掉应用级『允许通知』即可，验证码仍可在 App 内查看」。~~这段说明用灰色小字、还堆了实测细节~~ → **1.1.3.16 已改**：明文那句提升为橙色警告框，说明精简为「关掉『允许通知』或『实时活动』开关即可」，见 12.8。
4. ~~原本考虑在 `onRequestPermissionsResult` 记一个 `notifyDenied` 避免冷启动重复申请，实测后删掉：用户是从系统设置关的总闸，`checkSelfPermission` 多半仍是 granted，`nm.notify()` 被系统静默丢弃，不存在重复打扰。~~ → **这句判断错了，1.1.3.15 已推翻**：那次「实测」只覆盖了「不重启 App」的路径。AOSP 撤销 `POST_NOTIFICATIONS` 时会 `killUidForPermissionChange()` 杀进程，回到 App 是重建、内存标志归零，于是又弹一次权限请求。`notifyDenied` 这类持久化标记恰恰是必需的，详见 12.7。

**与第 13 节那条原则的关系**：「别在使用者设备上替对方做决定」在这里具体落成三件事——**不新增重复开关、不反复催促、把取舍和退出路径明说出来**。`VISIBILITY_PUBLIC` 与 `setOngoing(true)` 保持不变：它们是「锁屏直接看码」这个功能本身的定义，且已由总闸兜住，不需要 App 再 self-limit。

网页版不涉及锁屏通知，无需同步改动。`latest.json` 仍指向线上 1.1.3，未动。

**版本**：按约定继续留在 1.1.3.x，**1.1.3.13 / versionCode 24**。仅本地提交，未打 tag、未推送、未发布。

| `Notification.getShortCriticalText()` / `hasPromotableCharacteristics()` | ✅ public | 诊断直接调用 |
| `NotificationManager.canPostPromotedNotifications()` | ✅ public | 诊断直接调用 |
| `Notification.EXTRA_{SHOW_WHEN,SHOW_CHRONOMETER,COLORIZED,TEMPLATE}` | ✅ public 常量 | 换掉字符串字面量 |
| `Notification.Builder.setRequestPromotedOngoing(boolean)` | ❌ 未收录 | QPR1 才有；`ext19` 也没有 |
| `Notification.EXTRA_REQUEST_PROMOTED_ONGOING` | ❌ 未收录 | 同上 |
| `Manifest.permission.POST_PROMOTED_NOTIFICATIONS` | ❌ 未收录 | 清单里本来就是字符串，不受影响 |

所以**唯一保留的字面量**是 `android.requestPromotedOngoing`——但它是 `Bundle` 的数据键，不是反射、不是方法调用，而且正是 AndroidX 与 QPR1 平台共用的键名。等 public SDK 收录该常量即可一行替换。

**改动**：

1. `compileSdk` 升到 36：`build/build.sh` 的 `PLAT` 指向 `sdk/android-36/android.jar`（来自 `platform-36_r02.zip`）。**`targetSdkVersion=34` / `minSdkVersion=26` / `--target-sdk-version 34` / `--min-api 26` 全部不动**；`aapt2 link -I` 也仍用原来的 SDK 34 资源表，避免给低版本设备引入无谓的资源差异。升级范围严格限定在 Java 编译期类型检查。
2. 照 InstallerX 的 `ModernNotificationBuilder` / `LegacyNotificationBuilder` 结构做**按 SDK 分流**：所有 API 36 调用收进 `private static final class LiveUpdate36`，`SDK_INT >= Build.VERSION_CODES.BAKLAVA` 时才进入；低版本走纯 API 26 的分支，永远不加载这个类。`javap -c` 已验证 `BAKLAVA`、`FLAG_PROMOTED_ONGOING`、`EXTRA_*` 都被编译期内联成字面量，低版本不会触发类解析失败。
3. **反射清零**：`getMethod` / `Class.forName` 从 dex 中消失；`setShortCriticalText`、`canPostPromotedNotifications`、`hasPromotableCharacteristics`、`getShortCriticalText`、`setFlag` 全是直接 `invokevirtual`；样式改用 `EXTRA_TEMPLATE` 读回，不再反射 `getNotificationStyle()`。
4. **修掉上一轮指出的健壮性缺口**：`applyLiveUpdateFlavor()` 单独包 `try/catch(Throwable)`，外层 `notifyOrderCode` 也改成 `catch (Throwable)`。此前增强与 `nm.notify()` 同处一个 `try`，而 `NoSuchMethodError` 是 `Error` 不是 `Exception`，一旦某个 ROM 缺 API 36 方法就会把**整条普通通知一起吞掉**。现在无论增强发生什么，`nm.notify()` 都一定执行。
5. **「当日有效」加回** `BigTextStyle.bigText()`（两条分支都是 `room + " · 当日有效"`）。1.1.3.11 为了「像系统取单码卡片一样只有码」把它精简掉了，但 `contentText` 一直留着这句，实时活动展开时 `bigText` 覆盖 `contentText`，于是流体云上看不见——这次统一。
6. `tools/build.sh` 加了编译期下限检查：platform 低于 36 直接报错并提示 `ANDROID_PLATFORM=.../android-36`，不再让人看到一堆「找不到符号」猜原因。
7. 把 1.1.3.11 起不再适用的旧表格行（倒计时、全反射、任意 platform 可编译）用删除线标注。

**关于 Shizuku（明确不做）**：InstallerX 里的 Shizuku 属于安装器引擎的授权方式（`Authorizer.Shizuku`）；它唯一与通知相关的用法是 `SessionNotifierImpl.notifyWithXiaomiMagic()` —— 小米 MIUI 私有岛要临时切断 `xmsf` 进程网络来骗过系统校验，才需要 `appOps` 权限。那是**厂商私有路径**的 hack，和 AOSP 标准 Live Updates 无关。小米机型在 HyperOS 上走的是同一套 Google 标准，**本实现不申请 Shizuku、不新增任何权限、不做 MIUI 私有 extras 适配**；清单仍是 INTERNET / ACCESS_NETWORK_STATE / POST_NOTIFICATIONS / POST_PROMOTED_NOTIFICATIONS 四项。

**为什么不引入 AndroidX**：InstallerX 用 `NotificationCompat.Builder`，好处是兼容层替它处理版本差异。本项目是手工 `aapt2 + javac + d8` 的单 dex 构建（约 87 KB），引入 AAR 要处理资源合并、`R` 类冲突、传递依赖与体积膨胀。既然 compileSdk 36 已经让平台 API 直接可用，按 SDK 自己做一次分流即可达到同样的效果，不值得为此改构建链。

### 12.7 权限状态跨进程：一个系统机制引发的两个 bug（1.1.3.15）

**用户实测现象**：① 在系统设置里「开启通知」后，要重启软件才生效；② 「关闭通知」后回到软件，软件会重启，并且再次弹通知权限请求。

**先定性：软件重启是系统机制，不是 bug**。AOSP `PermissionManagerServiceImpl.java` 的 `PermissionCallback.onPermissionRevoked()` 里有：

```java
mHandler.post(() -> {
    if (POST_NOTIFICATIONS.equals(permissionName)
            && isAppBackupAndRestoreRunning(uid)) return;
    killUid(appId, userId, KILL_APP_REASON_PERMISSIONS_REVOKED);
});
```

`PermissionManagerService.killUid()` 的注释也直说「调用后应用可能立即重启」，内部走 `IActivityManager.killUidForPermissionChange()`。系统还专门留了 `revokePostNotificationPermissionWithoutKillForTest()` 给测试用——「WithoutKill」这个后缀本身就是反证。所以关掉通知 → 进程被杀 → 按返回键回 App 时重建 Activity、WebView 重新 `loadUrl`，看起来就是重启。第三方应用无法也不该阻止。

**关键的不对称**：`onPermissionGranted()` 只有 `onPermissionsChanged(uid)` 和 `writeSettings(true)`，**不杀进程**。App 还停在原进程里，`onResume()` 是唯一能感知到「权限刚被打开」的机会。两个 bug 都是这个不对称的下游后果：

| # | bug | 根因 |
| --- | --- | --- |
| 1 | 关掉权限回来又弹权限请求 | `notifyAsked` 只是个实例字段，进程被 kill 重建后归零；WebView 重新加载 → `loadAll()` → `renderOrder()` → `syncLockScreenCode()` → `showOrderCode()` → 权限检查失败 → 又调 `requestNotifyPermission()`。这直接违背 12.5 刚定的「尊重用户关掉通知的决定」 |
| 2 | 开启权限后要重启才生效 | `onResume()` 只调 `__onShow()`，而前端有 30 秒防抖；去设置页打个来回通常不到 30 秒，刷新被挡 → 不重新 `syncLockScreenCode()`。此外 `pendCode` 只在 `onRequestPermissionsResult()` 里补发，用户在系统设置里手动开权限**没有这个回调** |

12.5 里那句「实测不存在重复申请打扰，所以取消 `notifyDenied` 标记」被证伪：那次观察只覆盖了不重启 App 的路径。已用删除线保留并订正。

**改动**：

1. **把「用户决定」持久化到原生**。`SharedPreferences("bath")` 新增两个标记：`notifyPermAsked`（弹过一次系统权限对话框）、`notifyPermGrantedEver`（权限曾被授予过）。`requestNotifyPermission()` 只要任一为真就直接返回——**只在首次安装后第一次有预约时问一次**。标记在 `requestPermissions()` **之前**写，避免弹窗期间被杀进程后重建又弹。
2. **升级迁移** `migrateNotifyPermissionDecision()`：1.1.3.15 之前这两个键都不存在，老用户升级后第一次关权限仍会被弹一次。用「有登录态 token / phone」判定不是全新安装，直接记为已决定；当前有权限则记下「曾授予过」。全新安装仍保留首次问一次的机会。
3. **`onResume()` 检测权限状态变化**：记录 `lastNotifyPerm`，`false → true` 时补发挂起的 `pendCode`，并调 `__onShow(true)` 让前端绕过 30 秒防抖立刻 `loadAll()`；`onRequestPermissionsResult()` 授权成功时也强制刷一次，把首页提示和「我的」页状态同步更新。`onCreate()` 以当前真实权限为基线，避免首次启动被误判成「刚被打开」。
4. 前端 `window.__onShow(force)` 新增 `force` 参数，只影响防抖判断，弹层开着 / 未登录的保护不变。
5. **顺带修一个相关隐患**：`pendCode` 原先发出后不清空，用户取消预约再开关一次权限会把已取消的码复活。现在 `notifyOrderCode()` 发成功、`cancelOrderCode()` 都清空挂起内容。
6. `codeNotifyStatus()` 和 `notifyOrderCode()` 统一复用 `hasNotifyPermission()`，不再各写一遍 `checkSelfPermission`。

**验证时怎么区分**：从系统设置里**开启**通知 → 不杀进程，回来应立即出现通知与「已生效」，不需要重启也不用等 30 秒；**关闭**通知 → 系统会杀进程（这一步无法消除），回来后不应再弹权限对话框，「我的」页显示「已关闭」且没有提示框。

**版本**：按约定继续留在 1.1.3.x，**1.1.3.15 / versionCode 26**。仅本地提交，未打 tag、未推送、未发布。

### 12.11 真机回归的四个问题：状态延迟、三种说法、阈值的精度、顶部信息（1.1.3.19）

用户真机测试提出的四条，逐条对应：

**① 从系统设置页打开「实时活动」回来，状态不变，要下拉刷新才对**
1.1.3.15 修的是「关闭通知 → 打开通知」：那条路靠 `justGranted` 绕过 30 秒防抖。而「打开实时活动」不改变 `POST_NOTIFICATIONS`，`justGranted` 恒为 false，刷新被防抖挡掉——所以看着像同一个 bug，其实根因不同。

更深一层：**开关变了，已存在的通知对象不会自己重跑提升流程**。下拉刷新之所以有效，是因为 `loadAll → renderOrder → syncLockScreenCode` 又调了一次 `nm.notify()`，系统这才用新开关重新判定。所以修复不能只在 JS 里「重新读状态」，必须**重新提交通知**：

```js
window.__onShow = function (force) {
  const local = () => { renderOrder(); renderNotifyState(); };  // 重发通知 + 重画状态
  local(); setTimeout(local, 500); setTimeout(local, 1500);     // 提升是异步的，补读两次
  ...原有防抖与 loadAll
};
```

- 全部是本地调用，发网络请求的 `loadAll` 仍按 30 秒防抖，不会因为切来切去反复打服务器。
- 冷启动时 `state` 还是空的，若此时「重发通知」等于用空订单把上次进程留下的常驻通知清掉，等 `loadAll` 回来再补，中间闪一下。所以 `local()` 里先判 `state.cfg.hasToken`，没加载过就跳过。

**② 「已关闭 / 未开启 / 已生效」三种说法不直观**
「已关闭」和「未开启」在中文里几乎同义，用户分不清是「通知权限关了」还是「只是没上岛」。改成按**通知能到哪**命名：

| 状态 | 值 | 说明 |
| --- | --- | --- |
| 系统总开关关闭 | 通知已关闭 | 应用通知被关掉了：锁屏和状态栏都不会显示验证码。点这里重新开启。 |
| 通知在、实时活动没开 | **仅通知栏** | 通知能收到，但「实时活动」没开，所以锁屏上看不到验证码；点这里去打开。 |
| 实时活动生效 | **锁屏已显示** | 验证码正以“灵动岛”显示在锁屏 / 状态栏。 |
| 老设备（无实时活动） | 通知已开启 | 本机没有实时活动，验证码按普通通知显示，锁屏能否看到取决于系统设置。 |

前三种形成「没有 → 只在通知栏 → 到达锁屏」的递进，第四种单独说明，不再用两个近义词糊在一起。

**③ 阈值整数档不够用：1 元太早、2 元太晚**

「仅通知栏」意味着码在普通通知里，而普通通知会不会露在锁屏上，取决于系统设置——这件事原来只写了一句「锁屏显示与否看系统设置」，等于把判断丢给用户。现在先读，再按读到的结果说话：

原生 `lockScreenInfo()`（随 `notifyStatus` 的 `lock` 字段下发）：

| 字段 | 来源 | 含义 |
| --- | --- | --- |
| `canRead` | 两个键是否有值 | 读不到就退回「如果你开了…」的说明，不硬猜 |
| `show` | `Settings.Secure.lock_screen_show_notifications` | 锁屏是否显示通知 |
| `private` | `Settings.Secure.lock_screen_allow_private_notifications` | 锁屏是否显示敏感内容 |
| `secure` | `KeyguardManager.isDeviceSecure()` | 是否设了锁屏密码 |
| `channelVis` / `public` | 本应用通道的 `getLockscreenVisibility()` | 我们的通知是不是 PUBLIC |

`public` 这个字段是 honest disclosure 的关键：**1.1.3.4 起为了让验证码不被系统打码，通道锁屏可见性设的是 `VISIBILITY_PUBLIC`**，按 Android 语义它在所有锁屏上完整显示，系统「隐藏敏感内容」对它无效。所以当 `show=true` 且 `public=true` 时，提示不是含糊的「可能被别人看到」，而是明确告知：**系统那个开关挡不住，别人拿到手机不用解锁就能看到验证码**（还没设锁屏密码时再补一句）。

前端 `renderCodeWarn()` 按四种情况生成文案，并且**只在「通知在、但没上岛」时才讲这段风险**：上岛是用户自己选的（码在锁屏上是预期结果），通知全关了什么都不会显示（没必要吓人）。八种组合的桩测试全过。

### 12.14 锁屏提示读错了对象、测试包补齐归档（1.1.3.22）

**① `lock_screen_show_notifications` 不是「本应用会不会上锁屏」**
1.1.3.21 我按这个键判断，真机（ColorOS 16 / Android 16）立刻打脸：用户在本应用通知页**只开了「允许通知」，没勾「锁屏」**，锁屏确实不显示，可读到的仍是 `1`，于是提示成了「当前系统锁屏会显示通知内容」。

根因：这个键是**系统级默认值**，不是按应用的开关。ColorOS / HyperOS 这些 ROM 在本应用通知页里那个「锁屏」勾选项，存在厂商私有的通知设置里，**没有公开 API 可读**（1.1.3.21 试图用通道的 `getLockscreenVisibility()` 代替也不行——通道值是我们自己设的 PUBLIC，ROM 不会因为用户勾掉「锁屏」去改它）。

修正后的判定，只有一种情况能下肯定结论：

| 读到的 | 结论 |
| --- | --- |
| `systemShow == 0` | 系统级锁屏通知关了，可以确定不会显示 |
| `systemShow == 1` | 只说明系统默认开着；**本应用是否显示未知** |
| `-1`（读不到 / 被 ROM 限制） | 未知 |

所以前端只在 `systemShow == 0` 时说「系统级锁屏通知已关闭」，其余一律走「应用读不到」的说明：

> 锁屏会不会显示这条通知，应用读不到（各厂商在本应用的通知设置里还有按应用的「锁屏」开关）。如果锁屏能看到通知、又没开「锁屏隐藏通知内容」之类的开关，验证码可能被别人看到；需要解锁才能看到的话，安全程度会好一些。本应用的通知按「公开内容」提交，一旦真的显示在锁屏上，系统的隐藏开关也挡不住。

没设锁屏密码时再补一句。原生侧把原始三态作为 `systemShow` 一起下发（`show` 保留为兼容字段），并在注释里写清语义，避免下次又把它当成按应用开关。

**这条和 12.13③ 合起来的教训**：能读到一个值，不等于读到了想读的那件事。系统级默认值、按应用开关、通道设置是三个不同层次，混用会得出自信但错误的结论——这次是用户用真机把这个错误抓出来的。

**② 1.1.3.x 测试包全部归档到 `testbuild/`**
目录里原本只有 1.1.3.1~1.1.3.16：17~21 这几版我只留在 `android/build/bath.apk`，下一次构建就被覆盖了。处理：

### 12.17 那句免责提示为什么没显示、以及首次强制同意（1.1.3.25）

**① 提示不显示的根因：被提前返回挡住了**
1.1.3.24 把「风险由你自行承担」这句放在了 `renderCodeWarn()` 的**提前返回之后**：

```js
if (off || flagged) { box.innerHTML = out.join('<br>'); return; }   // 通知关了 / 已上岛
...  // ← 提示句写在这里，上面一 return 就到不了
```

用户装完 1.1.3.24 第一件事就是看设置页——**全新安装时 `POST_NOTIFICATIONS` 还是未授予状态**，`perm === false` 于是走「通知已关闭」分支直接返回，句子自然不出现。已经上岛的用户同样看不到。这和内容有没有写进 APK 无关（内检是过的），是控制流把话咽回去了。

修法：把责任声明移到提前返回**之前**，它和通知状态无关——不管用户开没开通知、上没上岛，责任边界都该写着。

**② 首次启动强制阅读并同意**
用户的原话：不强制的话，「免责声明」就是废纸。于是做成启动门槛：

- 全新安装（或未同意过）启动时，弹出**锁定**的 `#discFirst`：点外面、下拉、返回键都关不掉（`hideSheet()` 对锁定态直接 return）。
- 正文在 `max-height:44vh` 的滚动区里，**滑到底部才解禁「同意并继续」**，底部提示从「请向下滑动读完全文」变成「已读完全文，可以同意」。容差 8px，另在 300ms 后再判一次，防止内容不足一屏时按钮一直灰。
- 「不同意」调用新桥 `exitApp()` 退出（`finish()` 必须在主线程，桥方法跑在 WebView 桥线程，所以 `runOnUiThread`）。
- 同意标记存原生 SharedPreferences（键 `discAccepted`），理由同 `firstRunShown`：file:// 下 localStorage 不可靠，而这个标记决定能不能进主界面，丢了就等于重新强制一次。
- 存的是**声明版本号**（`DISC_VER = "1"`）而不是布尔值：条文改一次就把版本号加一，老用户的旧值对不上，下次启动重新征求同意。否则弹层里那句「内容变更时会重新征求同意」就是空话——初版写成永久 `"1"`，是我自己校对时发现的。

- 「设置 → 应用 → 免责声明」保留，随时可回看。

**关于「总有人不读就点同意」**：滚动解锁只能保证内容**经过**眼睛，保证不了**进**脑子。但这已经比一个直接可点的勾选框强——至少不会在完全没看到文本的情况下同意。真要更强只能加阅读计时或逐段确认，对一个洗澡预约工具来说过度了。

### 12.18 通知侧的场景化告知：该在发码那一刻说（1.1.3.26）

**先回答一个疑问**：通用免责声明只在**启动时**出现（首次或 `DISC_VER` 变化），和「打开系统通知页」没有任何联动——那个页面是系统的，App 没法也不该在那里弹自己的东西。

但用户的判断是对的：启动时同意的《免责声明》离「验证码马上要上锁屏」这个具体场景太远，两句风险声明淹没在一屏条文里。所以补一层**场景化告知**（分层告知）：

- 触发点是**第一次真正把码推进通知之后**（`renderOrder()` 末尾调 `maybeNotifyRisk()`），不是启动时、也不是打开设置页时。理由：风险在那一刻才产生，说明才有着力点。
- 只弹一次，标记 `notifyRiskAck` 单独存（与 `discAccepted` 分开：一个是启动门槛，一个是首次发码提醒，语义不同，合并会导致改一个条文把另一个也重置）。
- **不打扰的前提**：没有订单、通知没开（`st.ok` 为假）、或者已有别的弹层（比如刚点完预约的确认层），都不弹，留到下一次渲染。
- 弹层是锁定态（必须二选一）：**去系统设置** / **我知道了**，两者都记已读——去设置的人已经知道了，没必要下次再拦。
- 文案只讲三件事：码是明文、锁屏能看见就等于别人不用解锁也能看见、不想这样该关哪个开关。

**为什么不做成启动门槛**：启动时用户还没有验证码，讲「你的码会露在锁屏上」缺乏具体对象，容易滑过去；放在第一次发码后，用户刚看到通知栏里的码，此时说「它也会出现在锁屏上」才有直接对应物。**分层告知**（一般政策 + 场景提示）比把一切堆在首屏更符合「显著方式、清晰易懂」的要求，也不增加启动摩擦。

**验证**：`node --check` 过；APK 内检见构建记录。**版本 1.1.3.26 / versionCode 37**，仅本地提交，未推送。

### 12.21 第 9 条漏了「灵动岛」和息屏显示（1.1.3.29）

用户指出：政策第 9 条只写了「锁屏」，但被提升成“灵动岛”之后，验证码还会出现在**状态栏胶囊**和**息屏显示（AOD）**上——手机放在桌上、屏幕熄灭、没解锁，旁边的人也能直接看到。这比锁屏更难防：锁屏至少要点亮屏幕，息屏是「一直亮着」。

于是第 9 条重写为三层：

1. **说明形态**：常驻通知 + 请求系统提升为“灵动岛”（ColorOS 称流体云、澎湃 OS 叫实时动态），是否提升由系统决定。
2. **说明风险面**：一旦提升，验证码会出现在通知栏、锁屏、状态栏胶囊、息屏显示四个位置；「本应用无法限定它只在哪一层显示」——这是实时活动的系统行为，不是我们多加的开关。
3. **按影响范围排序关闭方式**：
   - 只关普通通知锁屏：系统设置 → 通知 → 本应用 → 关「锁屏」
   - 不让它上岛：关「实时活动」，**但只是退回普通通知，通知栏仍有码**
   - 彻底不显示：关「允许通知」，四个位置全部不出现

- 场景告知标题：`验证码会显示在锁屏上` → `验证码会显示在锁屏和息屏上`
- 场景告知正文：不再说「关锁屏就好」，改成「关实时活动只是降级，彻底不显示要关允许通知」
- 「验证码显示」注意事项首句：补上「开启灵动岛后连息屏也能看到，旁边的人不用解锁就能拿走」

**这类遗漏的教训**：写风险条款时要按「数据可能出现在几个地方」穷举，而不是按「用户最熟悉的那一个」写。锁屏是最容易被想到的，息屏恰恰是最难防的。

### 12.22 先讲风险、再申请通知权限（1.1.3.30）

**原来的顺序是反的。** 第一次取码时，JS 直接把码交给原生 `showOrderCode`，原生发现没有 `POST_NOTIFICATIONS` 就立刻弹系统权限框——用户看到的是「洗澡助手想要发送通知」，而那时他还不知道这条通知会把**明文验证码**送到锁屏、状态栏胶囊甚至息屏显示上。先同意、后知情，顺序错了。

改法：

1. `syncLockScreenCode()` 在交给原生之前先查 `notifyStatus().perm`。没权限时**不再调用** `showOrderCode`（否则会连带触发原生里的自动申请），而是弹一次前置说明 `#notifyPermAsk`。
2. 前置说明的两个出口：
   - **开启通知** → 调新桥 `askNotifyPermission()`（`runOnUiThread` 后走原来的 `requestNotifyPermission()`），这才弹系统权限框；授予后 `onResume` 的那次 `renderOrder` 会自动补发通知。
   - **暂不开启** → 记下已读、静默不发，也不反复问。**取码不受影响**，验证码在 App 内照常查看；以后在系统设置里打开，回前台即自动补发。
3. 文案里把风险点标红（`明文验证码`、`状态栏胶囊`、`锁屏`、`息屏显示`），并明确写「不给通知权限不影响取码」——这句话很重要：不写，用户会以为拒绝就不能用了，只能被迫同意。

**与 12.18 的关系**：那一版是在**发完码之后**再提醒（面向已经开了权限的用户），这一版把同样的内容前移到**申请权限之前**。两条路径共用 `notifyRiskAck` 标记，所以任一走过就不会再打扰；升级用户（权限早就开着）仍然会在首次发码后看到 12.18 那条。

**验证**：`node --check` 过；构建后 APK 内检见构建记录。**版本 1.1.3.30 / versionCode 41**，仅本地提交，未推送。

### 12.23 首次引导不再断言「密码是身份证后六位」（1.1.3.31）

用户去求证后得到两条互相矛盾的信息：

1. 他们学校**新生自己绑不上**，默认密码 `000000` 会触发完美校园的安全机制，必须先去师生服务平台找信息化处重置密码；
2. 但用户自己存疑——如果每个新生都要跑一趟信息化处，开学时那里早该忙疯了。

**两种说法都可能是真的（不同学院/批次流程不同），而这个 App 无从验证。** 原来的黄色提示里写死了「微信小程序 → 绑定校园卡 → 校园卡密码一般是身份证后六位，X 按 0 填」，把某一所学校某一段时间的经验当成了通用事实。一旦不成立，用户会以为是 App 有问题。

改法：

- **删掉整块黄色提示**（含绑定步骤与密码规则）；引导的浅灰正文里补一句「绑定方式与密码规则**以学校通知为准**：各校流程不一样——有的能直接在『完美校园』小程序里绑，有的需要先到信息化处重置密码」。
- 保留两个事实：小程序只能绑卡、没有「智慧用水」；绑完回本应用登录。
- 「打开微信」按钮保留（作为找到小程序的快捷入口），不再暗示「按这三步就能绑好」。

**原则**：涉及学校侧流程与密码策略的内容，应用层没有能力验证，就不要写成断言。宁可少写一步操作，也不要给一个会让用户白跑一趟的「标准流程」。

**验证**：`node --check` 过；引导里已无「身份证后六位」；构建后内检见记录。**版本 1.1.3.31 / versionCode 42**，仅本地提交，未推送。

**1.1.3.32 补**：上面那句「有的……有的……」仍然是穷举口气，用户要求再退一步——加「**据我所知**」，并明说「**肯定还有其他情况**（不同年级、不同批次的流程都可能不同）」。两次措辞调整指向同一件事：应用的作者只是使用者之一，不是学校流程的权威；列举只能作为线索，不能读成清单。**版本 1.1.3.32 / versionCode 43**。

**1.1.3.33 修排版**：用户发现手机上「能在」与「直接」之间多了个空格。原因是 HTML 源码里中文句子被硬换行，而浏览器会把换行折叠成一个空格——中文没有词间空格，这一折就露馅了。同一段里 `包含\n<span>明文验证码` 这种「文字 + 换行 + 行内标签」也会多出空格。

**1.1.3.34 修按钮权重**：用户指出申请通知权限的弹层里，「暂不开启」是描边按钮、「开启通知」是主色按钮且更宽——等于用视觉在推荐「开启」。这不是推荐场景，是需要用户自己权衡的选择，任何偏向都是操纵。改成两个描边按钮、等宽（`flex:1`）。**版本 1.1.3.34 / versionCode 45**。

**1.1.3.35 补两处死角**（用户问「点了开启通知、系统框里点拒绝会怎样」时查出来的）：

1. **拒绝后完全没有反馈**。`onRequestPermissionsResult` 原来只处理 `ok`，拒绝分支什么都不做：弹层已关、通知没发、界面照旧，用户会以为按钮坏了，之后取码发现锁屏没显示也不知道为什么。现在拒绝时回调前端 `__onNotifyDenied()`：刷新一次通知状态，并 toast「未开启通知：验证码仍可在 App 内查看；想开启请到「我的」页点通知状态」。
2. **「开启通知」可能是死的**。`requestNotifyPermission()` 在 `notifyPermissionDecided()` 时直接 return（问过/拒过就不再弹系统框），而新弹层的按钮只调它——对「以前拒过、现在想开」的用户，点按钮毫无反应。改成三路：已有权限 → 什么都不做；问过但没权限 → 直接送到系统通知设置页；从没问过 → 弹系统框。

**这一版重新确认了「拒绝」之后的完整状态**：不会反复弹（`notifyRiskAck` + 原生 `PREF_NOTIFY_ASKED` 都记下了）、不发通知、取码照常、**我的**页显示「通知已关闭」并可点进系统设置；以后在系统里手动打开，回前台那次 `onResume` 会自动补发，不需要重启。**版本 1.1.3.35 / versionCode 46**。

**1.1.3.36 账号卡片只留「我是谁」**：用户提议去掉手机号与登录态，同意。理由分别是——

- **手机号**：它是登录凭据的一部分，永久展示在设置页上没有任何收益，只是多一次被旁人看到的机会（宿舍场景尤其如此）。而登录框会自动带出上次的号码（`lgPhone` 预填 `cfg.phone`），真想确认账号时在那里看得到。这属于「展示层的最小必要」：能不看就不看。
- **登录态**：这是技术状态，不是用户需要读的信息。正常时是「有效」，一行废话；失效时应用会直接把首页换成「登录态已失效」并自动弹登录框，比一个静态的「缺失」清楚得多。一个字段在正常状态下无信息量、异常状态下又说不清，就该删。

**代价**：如果以后支持多账号切换，卡片上会缺少「当前是哪个号」的标识。目前只有单账号，等真做多账号时再加一行掩码手机号（`138****8888`）即可，不必现在预留。

## 13. 小结

从「想分析客户端」到「发现业务在 H5」，从「必须依赖额外权限与官方客户端」到「手机号 + 验证码纯登录」，从「一个能跑的网页」到「一份可覆盖安装、可审计、可回滚的 APK」——整个过程真正起作用的不是某个技巧，而是几次及时的**边界判断**：

- 业务在 H5，就不在原生层上纠缠；
- 登录态可以独立获得，就不做设备高权限方案；
- 微信支付绑死三者校验，就不做第二套支付；
- 服务端不校验时间，就从结构上删掉时间选择。

剩下的，就是把每次改动都配上可重复的验证，以及别在使用者设备上替对方做决定。

**外加一条，来自第 11 节的教训**：验证要能区分「公式自洽」和「事实成立」。一个算得出正确数字的公式，喂给它的输入可能是凭空假设的——那种验证只能证明推导没写错，证明不了世界是这样。
